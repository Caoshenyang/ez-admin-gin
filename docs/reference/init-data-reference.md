# 初始化数据参考

这页只回答一个高频问题：

> 第一次把系统跑起来时，哪些数据来自数据库脚本，哪些数据来自初始化接口？

## 当前初始化边界

当前主线固定分成两段：

1. 完整版 SQL 创建系统表和内置系统种子
2. `POST /api/v1/setup/init` 创建第一个管理员用户

也就是说：

- 内置角色、菜单、按钮、接口权限元数据、角色权限关联、Casbin 策略、字典、附件、通知权限种子来自数据库脚本
- 首个可登录管理员账号不内置在种子里，而是运行时创建

## 第一段：完整版 SQL 会写入什么

完整版 SQL 会落下面这些稳定锚点：

- `super_admin` 角色
- “权限管理 / 系统设置 / 审计监控”三类菜单树和按钮权限节点
- 系统接口权限元数据（`sys_api`）
- `super_admin` 对系统接口的角色接口关联（`sys_role_api`）
- 由接口元数据同步出来的 `super_admin` Casbin 策略
- 角色菜单关系
- 配置、字典、附件、部门、岗位、通知等主线模块的结构和内置系统数据
- 当前迁移基线，避免导入完整版 SQL 后启动服务时重复执行历史迁移

其中系统配置会内置一组已经接入业务逻辑的运行配置，覆盖 `rate_limit` 和 `upload` 分组。它们分别控制登录 IP 限流、账号失败锁定、文件上传大小和文件扩展名白名单。

| 配置键 | 影响范围 | 有效值 |
| --- | --- | --- |
| `rate_limit:login_max_requests` | 登录接口每 IP 在窗口期内允许的最大请求数 | `1` 到 `10000` |
| `rate_limit:login_window_sec` | 登录 IP 限流窗口秒数 | `1` 到 `86400` |
| `rate_limit:login_lockout_threshold` | 同一账号连续登录失败多少次后锁定 | `1` 到 `100` |
| `rate_limit:login_lockout_sec` | 账号失败锁定持续秒数 | `1` 到 `86400` |
| `upload:max_size_mb` | 文件管理和附件中心的单文件大小上限 | `1` 到 `50` |
| `upload:allowed_exts` | 文件管理和附件中心允许上传的扩展名 | 用逗号、分号、空格或换行分隔，例如 `.jpg,.png,.pdf` |

::: warning 运行配置边界
`sys_config` 只接管适合在线调整的业务运行参数。数据库、Redis、JWT secret、上传目录、CORS 等启动或安全根配置仍然来自 `server/configs/config.yaml` 和 `EZ_*` 环境变量；如果 `sys_config` 中的运行配置缺失、禁用或值非法，后端会回退到静态配置。
:::

当前内置种子还会顺手补齐一件容易被忽略的事：

- `super_admin` 的按钮节点授权
- `super_admin` 的接口权限元数据授权
- `super_admin` 的 Casbin 删除接口策略

也就是说，像用户、角色、菜单、部门、岗位、配置、字典、公告这些已经实现删除能力的模块，导入完整版 SQL 后就能直接删，不需要再手动补权限。

::: tip 当前删除能力边界
当前底座把“可管理实体删除”和“审计事实记录保留”分开处理：

- 支持逻辑删除：用户、角色、菜单、部门、岗位、配置、字典类型、字典项、公告
- 默认不提供单条删除：操作日志、登录日志
- 文件 / 附件仍以上传、编辑、状态管理为主，避免把物理文件生命周期和业务删除混成一层
:::

相关文件：

- `server/migrations/mysql/full_schema_and_seed.sql`
- `server/migrations/postgres/full_schema_and_seed.sql`

::: warning 初始化后请立即修改默认密码
当前项目明确把“系统骨架”和“首个运营账号”分开处理：SQL 不写入管理员账号，初始化接口运行时创建默认管理员 `admin / EzAdmin@123456`。

这样做的重点是：

- 避免数据库种子直接携带可登录用户
- 让初始化接口只在系统无用户时执行一次
- 首次登录后必须及时修改默认密码
:::

## 第二段：`setup/init` 会做什么

`POST /api/v1/setup/init` 负责：

1. 检查系统里是否已经存在用户
2. 使用默认账号 `admin / EzAdmin@123456` 创建第一条管理员用户
3. 自动绑定 `super_admin` 角色

当前实现依赖一个稳定前提：

- 数据库里必须已经存在角色编码 `super_admin`

因此正确顺序一定是：

```text
导入完整版 SQL
  ↓
系统具备 super_admin、菜单树、接口元数据、Casbin 策略
  ↓
POST /api/v1/setup/init
  ↓
创建首个管理员用户并绑定 super_admin
```

## 首次初始化命令

```bash
curl -X POST http://localhost:8080/api/v1/setup/init
```

执行成功后，你应该看到：

- `sys_user` 中出现首条管理员用户
- `sys_user_role` 中出现该用户与 `super_admin` 的绑定
- 接口返回提示你及时修改默认密码
- 再次执行会返回“系统已初始化”

## 当前最值得记住的约定

- 数据库脚本提供系统骨架，不提供真实管理员账号
- `super_admin` 是当前初始化链路的稳定角色锚点
- 完整版 SQL 是稳定初始化入口，不是历史迁移文件的简单拼接
- 菜单显隐和接口放行是两套配合关系：
  - `sys_menu` 负责前端菜单和按钮节点
  - `sys_api` 负责接口权限元数据
  - `sys_role_api` 负责角色接口权限关联
  - `casbin_rule` 负责 Casbin 运行时拦截
- 已经实现删除能力的模块，按钮节点、角色菜单、接口元数据、角色接口关联和 Casbin 策略要一起进种子，不能只补其中一层
- 完整版 SQL 是交付入口，增量迁移链是兼容和演进记录
