# 第 3 章：认证与登录态

前一章已经把后端基础设施搭好了：配置、日志、数据库、Redis、统一响应和路由入口都已经具备。现在开始补齐后台底座最核心的第一层安全能力：谁可以登录、登录后怎样维持登录态、服务端怎样稳定识别当前请求是谁。

::: tip 本章怎么验证
本章完成后，后端应该能完成登录认证，受保护接口需要携带有效 Token 才能访问，并能稳定返回当前登录用户摘要。
:::

::: info 当前主线已经收敛到最终版认证模块
当前代码里，`/api/v1/auth/login`、`/api/v1/auth/me`、`/api/v1/auth/menus` 和 `/api/v1/auth/dashboard` 这组入口已经统一收敛到 `server/internal/module/auth/`。后续本章正文也会继续按这套最终结构重写，而不是再扩旧的全局认证 Handler。
:::

## 开始前准备

进入本章前，建议先确认下面几件事：

- 后端可以正常启动。
- `/health` 和 `/api/v1/system/health` 都能返回成功响应。
- 本地数据库和 Redis 容器处于运行状态。
- 第二章中的统一响应、路由分组和健康检查已经完成。

::: warning ⚠️ 认证功能不要只看“能登录”
本章验证时不能只看登录接口是否返回 Token。还要确认：无 Token 会被拒绝，错误 Token 会被拒绝，权限不足也会被拒绝。
:::

## 本章会完成什么

本章会按下面的顺序推进：

| 小节 | 完成什么 | 验证重点 |
| --- | --- | --- |
| 用户模型与登录 | 创建用户表结构，提供用户名密码登录接口 | 正确账号能登录，错误账号或密码会失败 |
| Token 签发与解析 | 生成和解析登录 Token | Token 能表达用户身份和过期时间 |
| 登录校验中间件 | 保护需要登录的接口 | 不带 Token 不能访问受保护接口 |

::: details 为什么这一章先只收登录态
认证回答“你是谁”，接口权限回答“你能做什么”。如果还没有稳定的登录身份，就很难继续判断接口和菜单应该按谁的权限返回。
:::

## 当前代码入口

这一章现在主要优先对应下面这些认证入口：

| 接口 | 用途 |
| --- | --- |
| `/api/v1/auth/login` | 用户名密码登录并签发 Token |
| `/api/v1/auth/me` | 返回当前登录用户摘要和数据范围信息 |

完成本章后，后台底座会具备一条完整的安全链路：

```text
登录接口
  ↓

  ↓
当前用户摘要接口返回身份信息
```
