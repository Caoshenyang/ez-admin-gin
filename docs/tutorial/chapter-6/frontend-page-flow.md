# 前端页面接入流程

前面几页已经把后端模块结构讲清楚了，[第 7 章](../chapter-7/) 也已经把前端运行时主线立住了。现在轮到最容易在真实项目里失控的一步：

> 一个新模块的前端页面，到底应该按什么顺序接进当前管理台。

这一页不再按旧的“随手补个页面”思路写，而是直接对齐当前真实前端结构。

::: tip 🎯 本节目标
读完后，你应该能按当前主线顺序，把一个新模块的前端部分接进来：

1. 定义类型
2. 封装 API
3. 创建页面组件
4. 映射动态菜单组件
5. 接上按钮权限
:::

## 先看当前真实前端接入路径

在当前项目里，一个新页面真正进入后台，一般会经过下面这条链路：

```text
types/<module>.ts
  ↓
api/<module>.ts
  ↓
pages/<group>/<Module>View.vue
  ↓
router/dynamic-menu.ts
  ↓
后端 sys_menu.component
  ↓
登录后动态菜单和动态路由真正出现
```

这意味着前端页面接入不是“只新建一个 Vue 文件”，而是至少要让：

- 类型
- 接口
- 页面
- 动态路由映射
- 按钮权限消费

同时成立。

## 第一步：先定义类型

当前项目里，前端类型统一放在：

- `admin/src/types/`

这一步的目标，是先把“页面会和后端交换什么数据”固定下来。

以当前用户模块为例，`types/user.ts` 里已经包含：

- 状态常量
- 列表项结构
- 查询参数
- 列表响应结构
- 创建载荷
- 更新载荷
- 状态更新载荷
- 角色绑定载荷

当前这套写法很值得继续复用，因为它能让页面层和 API 层共享同一份数据结构。

## 当前类型文件建议长什么样

一个常规模块的类型文件，推荐至少包含下面这些部分：

```text
types/<module>.ts
├─ 状态常量 / 枚举
├─ XxxItem
├─ XxxListQuery
├─ XxxListResponse
├─ CreateXxxPayload
├─ UpdateXxxPayload
└─ 其他动作载荷
```

这里有几个当前主线里的固定约定：

- 字段名默认和后端 JSON 一致，优先使用 `snake_case`
- 状态值使用 `as const`
- 查询里的“全部”筛选通常用 `0`

也就是说，前端不会在类型层先把后端字段重新翻译成另一套命名，再在页面里来回转换。先对齐后端 JSON，会让整个链路更稳定。

## 第二步：再封装 API

当前所有接口封装都统一放在：

- `admin/src/api/`

并且所有资源 API 都依赖：

- `api/http.ts`

这意味着新增模块时，你不需要再重新处理：

- Axios 实例
- `Authorization` 请求头
- 401 清理逻辑

你只需要围绕这个模块自己的后端接口，把具体方法补出来。

例如当前用户模块就是：

- `getUsers`
- `createUser`
- `updateUser`
- `updateUserStatus`
- `updateUserRoles`

这一层解决的是：

> 页面不直接写请求细节，而是面向清晰的资源级 API 函数工作。

## 当前 API 文件的最小形态

一个常规管理页模块，前端 API 文件通常至少会有：

- 列表查询
- 创建
- 编辑
- 状态更新

如果这个资源还带额外动作，例如：

- 分配角色
- 分配菜单
- 上传文件
- 读取配置值

再继续补对应方法即可。

## 第三步：创建页面组件

当前系统页面主要落在：

- `admin/src/pages/system/`

如果后续补真实业务模块，最自然的延续就是新增新的页面分组目录，而不是继续把所有页面都塞进 `system/`。

当前一个典型管理页，大体会包含下面这些部分：

```text
<script setup>
├─ 导入 API / types / buttonPermissionCodes
├─ 列表状态
├─ 查询条件
├─ 表单状态
├─ 表格列定义
├─ loadXxx()
├─ openCreate() / openEdit()
├─ handleSubmit()
└─ canUse()

<template>
├─ 页面标题与操作区
├─ 搜索卡片
├─ 表格卡片
├─ 分页
└─ 新增 / 编辑弹窗
```

以当前 `pages/system/UserView.vue` 和 `pages/system/NoticeView.vue` 来看，这套结构已经很稳定了。

## 为什么当前页面普遍围绕“搜索 + 表格 + 弹窗”展开

这不是样式习惯，而是当前后台底座有意识选择的一种通用管理页模式。

它的好处是：

- 模块之间交互心智一致
- 列表页和编辑页不必强行拆成两套路由
- 小型和中型后台最常见的操作形态都能覆盖

也就是说，”页面接入规范”不仅是文件放哪里，还包括页面交互模式尽量稳定。

## 第四步：把页面接进动态菜单映射

页面写完后，还不能直接被后台菜单打开。因为当前系统不是手写静态业务路由表，而是围绕：

- `/api/v1/auth/menus`

的菜单树动态生成页面路由。

所以新页面还必须补一层：

- `admin/src/router/dynamic-menu.ts`

里的 `routeComponentMap`。

这一步非常关键，因为后端菜单里的 `component` 字段，最终就要命中这里的 key。

例如当前已有：

- `system/UserView`
- `system/RoleView`
- `system/NoticeView`

只要数据库里的菜单 `component` 值和这里不一致，前端就会回退到占位页。

## 第五步：按钮权限怎么接

当前页面按钮权限统一来自：

- `buttonPermissionCodes`

页面层通常会写一个很轻的辅助函数：

```ts
function canUse(code: string) {
  return buttonPermissionCodes.value.includes(code)
}
```

再在按钮上用：

```vue
v-if="canUse('system:user:create')"
```

控制显隐。

这一层的意义是：

- 页面按钮不靠硬编码角色判断
- 页面按钮权限直接服从后端菜单树里的按钮节点授权结果

## 为什么“页面能打开”和“按钮能显示”是两回事

这是新增模块时最容易漏掉的一点。

当前前端里，页面级接入至少有两层：

| 层 | 作用 |
| --- | --- |
| 页面菜单节点 | 决定路由和侧边栏入口 |
| 按钮权限节点 | 决定页面内具体操作显隐 |

所以即使新页面已经：

- 有页面文件
- 有动态路由映射
- 有菜单入口

如果没补按钮权限节点，页面里很多操作按钮依然会不显示。

## 当前后端菜单字段和前端页面接入怎么对齐

接一个前端页面时，至少要同时对齐下面几项：

| 后端菜单字段 | 前端对应点 |
| --- | --- |
| `path` | 最终页面访问路径 |
| `component` | `dynamic-menu.ts` 中的映射 key |
| `code` | 页面菜单编码 / 按钮权限编码 |
| `icon` | 图标白名单映射 |

这也说明前端页面接入从来不是“前端单边完成”的事情，而是和第 6 章的菜单、权限、迁移种子直接联动的。

## 一个新模块的最小前端接入清单

如果你现在要新增一个典型管理页模块，最小前端步骤通常是：

1. 新建 `types/<module>.ts`
2. 新建 `api/<module>.ts`
3. 新建 `pages/<group>/<Module>View.vue`
4. 在 `dynamic-menu.ts` 里补 `routeComponentMap`
5. 页面里接入 `buttonPermissionCodes`
6. 对照后端菜单种子确认 `component` 和按钮 `code` 一致

## 当前主线下几个常见易错点

### 1. `component` 映射不一致

后端种子写的是：

- `business/OrderView`

前端却写成：

- `business/orders/OrderView`

这时页面通常会掉到占位页，而不是目标页面。

### 2. 页面按钮权限码和菜单按钮节点不一致

页面里写的是：

- `business:order:create`

但后端按钮节点种子里写成：

- `business:orders:create`

这时页面按钮会一直不显示。

### 3. API 方法没沿当前接口风格走

当前后端大量写操作仍然使用：

- `POST /:id/update`
- `POST /:id/status`

如果前端习惯性封成 `PUT /:id`，就会直接对不上。

## 怎么验证这一页讲的流程已经成立

### 1. 登录后能在侧边栏看到新页面入口

这说明：

- 页面菜单节点已写入后端
- 菜单树返回正常
- 动态菜单映射成功

### 2. 点击菜单进入的是目标页面，不是占位页

这说明：

- `component` 字段
- `routeComponentMap`
- 页面文件路径

这三者已经对齐。

### 3. 页面能正常调接口并展示数据

这说明：

- `types/*`
- `api/*`
- 页面脚本

三层已经开始形成闭环。

### 4. 按钮会随着按钮权限码变化而显隐

这说明：

- 页面已经正确接入 `buttonPermissionCodes`
- 后端按钮节点也已经真正进入 `/auth/menus`

## 本节最关键的结论

这一页真正要建立的判断是：

> 当前前端页面接入，不是“写一个 Vue 页面再补几条 API”，而是把类型、请求、页面、菜单映射和按钮权限一起接进已有运行时系统。

只要你后面新增模块时沿这条线继续扩，前端就不会从“统一后台”慢慢退化成“一堆分散页面”。

下一步再结合前面几页和第 7 章的主线，把一个真实模块完整跑通看，会更容易建立整体感。
