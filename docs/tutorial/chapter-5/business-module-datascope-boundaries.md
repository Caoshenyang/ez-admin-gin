# 真实业务模块的数据权限边界

第 5 章前面几页已经把平台层规则和系统模块接法讲清楚了。  
但真正到了新项目里，更常见的问题其实是：

> 一个新的业务资源，到底该接哪种数据权限模式，还是说它根本不该在这一阶段接数据权限。

这一页就是专门解决这个判断问题。

::: tip 🎯 本节目标
读完后，你应该能先判断一个真实业务模块属于哪一类资源，再决定它该接：

1. `UserQueryScope(...)`
2. `DepartmentQueryScope(...)`
3. 暂时显式放开
:::

## 先记住一个最重要的前提

当前底座的数据权限，不是“所有模块都必须套一层过滤”的模板，而是：

> 先看资源和组织体系之间有没有稳定关系，再决定要不要接入数据权限。

如果关系本身都还没定稳，就硬把模块塞进 Scope 里，后面通常只会得到：

- 查询条件很绕
- 维护成本很高
- 角色解释越来越混乱

所以在接真实业务模块前，最值得先问的不是“能不能加 Scope”，而是：

- 这个资源是不是天然归属于某个部门
- 它是不是同时退化成“本人数据”
- 它本身是不是组织节点
- 它是不是更像系统级字典或配置

## 先用当前三种已落地模式当模板

当前仓库已经给了三种很典型的接法：

| 模式 | 当前代表模块 | 适合什么资源 |
| --- | --- | --- |
| 部门归属 + 本人退化 | `user` | 业务单据、客户、线索、工单、审批单等 |
| 节点自身可见性 | `department` | 部门树、组织单元、区域节点、分类树等 |
| 当前先显式放开 | `post` | 岗位、系统字典、固定配置类资源 |

这三种模式已经足够覆盖大多数后台首版业务资源。

## 第一类：归属于部门，也可能退化到本人

这是最常见、也最适合直接复用当前主线的一类。

### 典型特征

- 资源记录天然属于某个组织单元
- 资源也可能需要支持“仅本人可见”
- 同一个列表通常既要按部门范围过滤，也要支持本人退化

### 常见例子

- 业务客户
- 销售机会
- 工单
- 审批单
- 项目任务
- 线索池中的个人线索

### 当前最适合的接法

这类资源最接近当前用户模块：

```go
return db.Scopes(datascope.UserQueryScope(db, actor, "department_id", "owner_id"))
```

其中：

- `department_id` 表示资源归属部门
- `owner_id` 表示资源负责人或创建人

### 什么时候不要直接照抄用户模块

如果你的业务资源没有“本人退化”语义，例如它只允许按部门维度看，而不允许 `self` 单独退化，那么就不要为了复用而硬塞一个 `owner_id`。

此时更稳的做法是：

- 仍然沿用当前平台层并集规则
- 但在模块内只声明部门相关列

## 第二类：资源本身就是范围节点

这类资源不是“属于部门”，而是自己就代表可见范围节点。

### 典型特征

- 它本身是一棵树或一组层级节点
- 当前用户能不能看它，判断的是“这个节点在不在授权范围内”
- 不是看“它属于哪个部门”

### 常见例子

- 部门树
- 区域树
- 业务分类树
- 渠道层级

### 当前最适合的接法

这类资源最接近当前部门模块：

```go
return db.Scopes(datascope.DepartmentQueryScope(db, actor, "id"))
```

核心含义是：

- 直接按资源节点 ID 判断可见性
- `dept_and_children` 时按节点子树展开
- `custom_dept` 时按授权节点集合命中

## 第三类：系统级字典或当前先不裁剪的资源

这类资源在首版里非常常见，但也最容易被误判。

### 典型特征

- 它不是组织树节点
- 它也不一定天然归属于部门
- 首版里更像“系统级公共资源”

### 常见例子

- 岗位
- 数据字典
- 全局配置项
- 固定模板
- 公共通知类型

### 当前更合适的做法

这类资源通常更适合像岗位模块一样：

```go
func applyDataScope(db *gorm.DB) *gorm.DB {
	return db
}
```

关键不在于“偷懒”，而在于：

- 当前业务边界还没逼出组织过滤需求
- 先显式放开，能避免过早引入错误的部门耦合

## 一个新模块到底该怎么选

如果你今天要新增一个真实业务模块，可以直接按这张表判断：

| 先回答的问题 | 如果答案是“是” | 更接近哪种模式 |
| --- | --- | --- |
| 资源是否天然归属于部门或团队 | 是 | `UserQueryScope(...)` 类 |
| 资源是否需要支持“仅本人可见” | 是 | `UserQueryScope(...)` 类 |
| 资源本身是不是层级节点 | 是 | `DepartmentQueryScope(...)` 类 |
| 资源是不是系统级公共字典 | 是 | 当前显式放开 |
| 资源关系还没定稳 | 是 | 先显式放开，不急着强套 Scope |

## 为什么不要一开始就发明“第四种 Scope”

当前平台层已经有：

- `UserQueryScope(...)`
- `DepartmentQueryScope(...)`

再加上模块层的显式放开，已经足够支撑首版大量资源。

如果一开始就为每个业务模块再发明一套新 Scope，最容易出现的问题是：

- 每个模块的语义都不一样
- 并集规则开始分叉
- 后面很难再把它们统一回平台层

所以更稳的策略通常是：

1. 先尽量落进现有三种模式
2. 真的遇到第四类资源，再抽新的平台级能力

## 什么情况下才值得收紧到“新 Scope”

只有当下面三件事同时成立时，才值得考虑新增平台级 Scope：

1. 当前三种模式都表达不准
2. 这个资源模式会重复出现在多个模块里
3. 你能明确写出统一语义，而不是只为一个模块临时服务

换句话说，只有当它已经是一类稳定资源，不再只是单模块例外时，才值得升级到平台层能力。

## 这页和第 6 章是什么关系

第 5 章解决的是：

- 数据权限语义是什么
- 模块该接哪一类过滤

第 6 章解决的是：

- 一个模块从后端到前端到底怎么接入

所以更合理的阅读顺序通常是：

1. 先在第 5 章判断资源属于哪种数据权限模式
2. 再去第 6 章按模块接入清单把代码接完整

## 怎么验证这套判断真的有用

如果你现在拿一个新业务模块来套，至少应该能做出下面三个判断：

1. 它到底是“归属于部门的资源”，还是“节点资源”
2. 它有没有 `self` 退化语义
3. 它现在是不是更适合先显式放开

只要这三步先想清楚，后面的 `datascope.go` 基本就不会乱。
