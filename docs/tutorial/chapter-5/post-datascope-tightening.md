# 岗位资源的数据权限收紧时机

第 5 章里，岗位模块是一个很容易让人犹豫的例子。

因为它明明已经进入了统一模块结构，也已经接进了用户归属关系，但当前 `post/datascope.go` 里却还是：

```go
func applyDataScope(db *gorm.DB) *gorm.DB {
	return db
}
```

这不是漏接，而是一个有意识的设计取舍。

::: tip 🎯 本节目标
读完后，你应该能判断：

1. 岗位资源为什么当前不按部门范围裁剪
2. 什么时候这种放开仍然是合理的
3. 什么时候才值得把岗位资源真正收紧进数据权限链路
:::

## 先看当前真实代码边界

岗位模块现在的真实状态是：

- 已经有独立的 `iam/post` 模块
- 已经有自己的 `datascope.go`
- 用户和岗位关系已经通过 `sys_user_post` 接进用户模块
- 但岗位资源本身还没有声明组织归属字段

这意味着当前系统里已经成立的是：

- 用户挂了哪些岗位

但还没有成立的是：

- 某个岗位属于哪个部门
- 某个岗位只在某个组织子树里生效

## 为什么当前先显式放开更稳

如果现在就强行让岗位资源按部门过滤，最先会遇到的问题是：

- 过滤依据从哪里来
- 岗位到底按创建部门、使用部门，还是主负责部门过滤
- 同一个岗位能不能被多个部门复用

在这些问题还没有稳定答案之前，硬加数据权限通常只会制造伪规则。

所以当前主线选择的是：

> 岗位先作为系统级组织字典处理，把“岗位是什么”先定稳，再决定“岗位对谁可见”。

## 当前岗位资源更像哪类资源

从数据权限角度看，岗位当前更接近：

- 系统级公共字典

而不是：

- 部门节点
- 带部门归属的业务资源

因为它当前承担的职责更像：

- 给用户做岗位标签
- 给前端提供可选岗位列表
- 让系统具备基础的人事组织表达能力

而不是控制“只有哪个部门才能看到哪个岗位”。

## 什么情况下继续放开是合理的

如果你的项目里，岗位满足下面大多数条件，那么继续放开通常是合理的：

1. 岗位是全局公共岗位字典
2. 同一个岗位编码会被多个部门共同使用
3. 用户只是在岗位集合里选身份标签
4. 岗位列表本身不承载敏感业务数据

这种情况下，强行给岗位加部门过滤，往往只会增加维护成本。

## 什么时候开始需要收紧

只有当岗位开始具备明显组织边界时，才值得考虑收紧。例如：

- 不同部门维护自己的岗位集合
- 同名岗位在不同部门语义不同
- 岗位已经成为审批、流程、可见范围的一部分
- 岗位本身开始参与组织授权或业务分配

一旦出现这些特征，岗位就不再只是“系统字典”，而会更接近：

- 带部门归属的资源

## 如果未来要收紧，最先要补什么

在当前结构里，未来如果真的要把岗位收紧进数据权限链路，最应该先补的不是 Scope，而是资源模型本身。

至少要先明确下面几个问题：

1. 岗位是否新增 `department_id`
2. 一个岗位是否只属于一个部门
3. 还是要引入岗位和部门的多对多关系
4. 用户岗位关系是否继续保持现在的结构

在这些前置关系没定稳之前，`datascope.go` 里的过滤条件其实没有可靠落点。

## 未来最可能落成哪种接法

如果未来岗位明确归属于某个部门，最可能的收紧方式不是新增一套独立平台语义，而是复用当前第一类资源模式：

```go
return db.Scopes(datascope.UserQueryScope(db, actor, "department_id", ""))
```

或者按岗位最终模型，声明更合适的部门字段。

因为从本质上看，那时岗位就已经变成：

- 归属于部门的资源

而不再只是全局字典。

## 什么时候仍然不值得收紧

即使未来岗位功能更丰富，只要它仍然满足下面条件，就依然不值得急着接部门过滤：

- 岗位只是用户属性标签
- 业务敏感信息不在岗位表里
- 真正敏感的是挂岗位的用户或业务单据，而不是岗位本身

这时更应该重点控制的，仍然是：

- 用户资源
- 业务资源

而不是岗位字典列表。

## 当前这件事给第 5 章什么提醒

岗位模块的这个例子，其实正好说明了第 5 章最重要的一个方法论：

> 数据权限不是“看到模块就套过滤”，而是先看资源边界，再决定是否需要过滤。

如果一个资源的组织归属关系还没成立，显式放开往往比仓促收紧更稳。

## 怎么验证当前判断没有跑偏

你可以直接用下面三条判断当前岗位模块：

1. `GET /api/v1/system/posts` 现在仍然返回系统级岗位列表
2. 用户岗位关系已经能在用户模块里维护
3. 岗位表本身没有稳定的部门归属字段

只要这三件事都成立，当前把岗位资源显式放开就是合理的。
