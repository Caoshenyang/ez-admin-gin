# 共享数据权限接入规范

第 5 章前面几页已经把平台规则、典型资源和岗位边界讲清楚了。  
但如果后续要继续扩模块，还差最后一件很实用的东西：

> 如何把这些接法收成一套统一规范，让后面的模块都沿着同一条线接入，而不是每加一个模块就重新解释一遍数据权限。

这一页专门解决这个问题。

::: tip 🎯 本节目标
读完后，你应该能用同一套判断顺序处理下面四类模块：

- `user` 这类“部门归属 + 本人退化”资源
- `department` 这类“节点自身可见性”资源
- `post` 这类“当前先显式放开”的资源
- 以后新增的真实业务模块
:::

::: info 这一页只负责“先选哪种模式”
这一页重点解决的是：

- 新模块更接近哪类资源
- 它应该先选哪种 Scope

如果你想先把当前已经存在的三类模式本身看清楚，优先读：

- [资源级数据权限接入模式](./module-datascope-patterns)

如果你已经知道模块该选哪种模式，接下来真正要看代码落点，优先读：

- [datascope.go 与 Repository 边界](./datascope-and-repository-boundary)
- [一次完整请求的权限过滤走读](./request-flow-walkthrough)
:::

## 先记住当前真正要复用的不是某个函数，而是一条判断顺序

当前仓库里最值得复用的，不只是：

- `UserQueryScope(...)`
- `DepartmentQueryScope(...)`

而是它们背后的整条接入顺序：

```text
先判断资源边界
  ↓
再决定它更接近哪类现成模式
  ↓
真的三类都表达不准，再考虑要不要抽第四种平台语义
  ↓
模式选定后，再交给模块内落代码
```

这条顺序一旦稳定，后面无论扩 `system` 模块还是扩真实业务模块，数据权限都不会散。

## 当前统一接入规范的四步判断

如果你要给一个新模块接数据权限，当前最稳的顺序是下面四步。

### 第一步：先判断资源和组织体系是什么关系

不要一上来就问“这个模块能不能套 Scope”，而要先问：

1. 这个资源是不是归属于某个部门
2. 它会不会退化成“仅本人可见”
3. 它本身是不是组织节点
4. 它现在是不是更像系统级字典

这一步判断错了，后面整条数据权限链路都会跑偏。

## 第二步：把资源先归进当前三种已知模式

当前项目已经有三种稳定接法：

| 模式 | 当前代表 | 核心判断 |
| --- | --- | --- |
| `UserQueryScope(...)` | `user` | 资源归属于部门，也可能退化到本人 |
| `DepartmentQueryScope(...)` | `department` | 资源本身就是范围节点 |
| 显式放开 | `post` | 当前更像系统级公共字典 |

后续真实业务模块，优先先往这三种模式里落，而不是急着发明第四种平台语义。

## 第三步：能落进现有三种模式，就先不要急着抽第四种 Scope

这一页里最重要的判断不是“代码先怎么写”，而是：

> 当前这个新资源，到底有没有必要升级出第四种平台级语义？

默认答案应该是：先不要。

因为一旦你还能自然把它解释成：

- `user` 型
- `department` 型
- `post` 型

那就说明这件事还没有复杂到需要新增一套平台语义。

## 第四步：模式选定后，再把它交给模块内代码落地

当前这页只把你带到“模式已经选对”这一步。

接下来真正的代码落点是：

1. 在模块自己的 `datascope.go` 里声明字段
2. 在 Repository 入口统一先套 `applyDataScope(...)`

这一层不再在这里展开，是因为它已经属于下一页的职责边界：

- [datascope.go 与 Repository 边界](./datascope-and-repository-boundary)

## 最后把它压成一张可执行判断表

如果你在接一个新模块，不想每次都把第 5 章整章重新翻一遍，可以直接按下面这个顺序判断：

| 先问什么 | 如果答案是这样 | 当前建议 |
| --- | --- | --- |
| 资源是不是“属于某个部门，也可能只看本人” | 是 | 先按 `UserQueryScope(...)` 接 |
| 资源本身是不是树节点或范围节点 | 是 | 先按 `DepartmentQueryScope(...)` 接 |
| 资源当前是不是更像系统级公共字典 | 是 | 先显式放开 |
| 三种都解释不准，而且多个模块都会反复遇到 | 是 | 再评估是否值得抽第四种平台语义 |

这张表真正想固定的是一条主线：

- 先靠现成模式解释
- 再进入模块内代码落地
- 最后才考虑平台抽象升级

## 当前四类模块可以怎么套这套规范

### 1. `user` 类模块

当前用户模块的判断方式是：

- 资源归属于部门
- 也允许 `self` 退化成只看自己

所以它最终会落向 `UserQueryScope(...)` 这一路。

如果你以后做：

- 客户
- 工单
- 项目任务
- 审批单

而且这些资源也同时具备“部门归属 + 本人负责”语义，那么大概率也应先按这一路来接。

### 2. `department` 类模块

部门模块的判断方式是：

- 资源自己就是范围节点
- 判断的是“这个节点在不在可见范围内”

所以它最终会落向 `DepartmentQueryScope(...)` 这一路。

如果你以后做：

- 区域树
- 分类树
- 组织单元树

而它们本身也承载范围节点语义，那么就更接近这一路。

### 3. `post` 类模块

岗位模块当前的判断方式是：

- 已经进入最终结构
- 但岗位本身还没有稳定组织归属字段
- 更像系统级公共字典

所以它当前会落向“显式放开”这一路。

这一点要理解成：

- 不是漏接
- 而是当前阶段的显式边界

### 4. 真实业务模块

真实业务模块最容易犯的错是：

- 看见系统模块用了 Scope，就机械照抄

当前更稳的顺序应该是：

1. 先判断它到底更像 `user`、`department` 还是 `post`
2. 能落进现有三种模式就先落进去
3. 真的三种都表达不准，再考虑抽第四种平台级语义

## 当前为什么不建议每个模块各写一套“定制权限逻辑”

因为这样很快会出现三种问题：

1. 多角色并集开始在不同模块里出现不同解释
2. `self` 退化规则在某些模块里丢失
3. 排查“为什么这个人能看 A 不能看 B”时没有统一入口

而当前这套接入规范的价值就在于：

> 平台层统一保留少量稳定语义，模块层和新模块先学会套用，而不是先扩语义。

## 什么时候才值得抽第四种 Scope

只有当下面三件事同时成立时，才值得继续往平台层抽新能力：

1. 现有三种模式都表达不准
2. 这个模式会在多个模块里反复出现
3. 你能先说清楚稳定语义，再动代码

换句话说：

- 单模块例外，不值得立刻升级成平台能力
- 多模块共享且语义稳定，才值得收口成第四种 Scope

## 这页和第 6 章的边界

这一页回答的是：

- 数据权限到底该怎么接
- 新模块该选哪种过滤模式

第 6 章回答的是：

- 一个模块从后端到前端怎样完整接入

所以更顺的阅读顺序通常是：

1. 在第 5 章先把数据权限模式选对
2. 再去第 6 章按模块接入清单把整条链路接完

## 怎么判断当前这套规范已经收稳

如果第 5 章收稳了，你应该能很自然地回答下面四个问题：

1. 一个新资源为什么更接近 `UserQueryScope(...)`、`DepartmentQueryScope(...)` 还是显式放开
2. 为什么岗位模块当前保留显式放开
3. 为什么大部分新模块都应该先靠现成三种模式解释
4. 为什么模式选定后，不应该立刻再发明第四套平台语义

只要这四个判断已经稳定，后续模块接数据权限时就不需要再从零讨论。
