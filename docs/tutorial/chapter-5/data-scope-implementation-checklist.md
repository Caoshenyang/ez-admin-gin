# 数据权限落地检查清单

第 5 章前面已经分别讲了：

- 组织模型为什么要先定稳
- `Actor` 和多角色并集怎么形成
- `datascope.go` 和 Repository 该怎么分工
- 一次真实请求如何从中间件走到查询过滤

但真实开发里，最容易出问题的地方并不是“不知道这些概念”，而是：

> 代码看起来都补了，可这个模块其实还没有真正进入第 5 章的数据权限主线。

这一页就是专门拿来做最后验收的。

::: tip 🎯 本节目标
读完后，你应该能拿这份清单去检查一个模块，判断它是否真的完成了：

- 组织归属建模
- `Actor` 接入
- `datascope.go` 声明
- Repository 统一过滤
- 列表、详情、更新前检查一致
:::

## 先给结论：数据权限接入完成至少要过六关

如果一个模块真要算接好了第 5 章的数据权限，至少要同时过下面六关：

1. 资源和组织体系之间的关系已经先判断清楚
2. 当前登录人的 `Actor` 上下文已经能提供这个模块需要的范围事实
3. 模块已经明确落到某一类 `Scope` 接法上
4. Repository 入口已经统一先套权限边界
5. 单条资源查询和写操作前检查也复用了同一边界
6. 不同角色手工验证时，结果真的会按预期变化

也就是说，这件事的判断标准不是：

- “我在列表里多写了一条 `Where`”

而是：

```text
资源边界判断正确
  ↓
请求上下文准备完整
  ↓
模块声明层落位
  ↓
Repository 过滤生效
  ↓
更新前查询不越界
  ↓
真实角色验证通过
```

## 第一关：资源边界是不是先判断清楚了

第 5 章当前最重要的前置判断不是写代码，而是先回答：

1. 这个资源是否归属于部门
2. 它是否需要退化成“仅本人可见”
3. 它本身是不是范围节点
4. 它现在是不是更像系统级公共字典

这一步如果没想清楚，后面的 `datascope.go` 很容易写成错误方向。

### 这一关通过后，应该得到什么

你至少应该能明确说出这个模块更接近哪一种：

- `UserQueryScope(...)`
- `DepartmentQueryScope(...)`
- 当前显式放开

### 这一步常见失败信号

- 明明是系统级字典，却硬套部门过滤
- 明明是范围节点，却照抄了用户模块接法
- 只因为“别的模块也用了 Scope”，就机械复制

## 第二关：`Actor` 是不是已经够这个模块用

当前第 5 章的主线前提是：

- 数据权限不由模块自己重新查角色
- 而是依赖统一的 `Actor`

所以你要先确认，这个模块真正需要的东西是否都已经在：

- `UserID`
- `DepartmentID`
- `RoleCodes`
- `Grants`
- `IsSuperAdmin`

这套上下文里表达出来了。

### 这一关通过后，应该看到什么

- Handler 或 Service 不再自己重新查当前用户角色
- 模块能直接消费 `Actor`
- 多角色语义仍然统一来自平台层

### 这一步常见失败信号

- 模块里又自己写了一遍“查当前用户角色”
- `self`、`custom_dept` 逻辑在模块里单独重算
- 超级管理员放行规则散落在业务代码里

## 第三关：模块自己的 `datascope.go` 是否已经落稳

当前第 5 章要求每个需要数据权限的模块，都把资源声明层固定在自己的：

- `datascope.go`

里。

这层的职责只有一个：

- 声明“这个资源按哪个字段接 Scope”

例如：

```go
return db.Scopes(datascope.UserQueryScope(db, actor, "department_id", "id"))
```

### 这一关通过后，应该看到什么

- 模块里存在明确的 `applyDataScope(...)`
- 资源字段声明集中在一个地方
- Handler / Service 不再到处散写 Scope 入口

### 这一步常见失败信号

- `gorm.Scopes(...)` 散在多个 Repository 方法里
- 模块自己重写了并集逻辑
- 同一模块不同方法套了不同过滤字段

## 第四关：Repository 是否始终先套权限边界

当前更稳的顺序必须是：

1. 先 `applyDataScope(...)`
2. 再叠 `keyword`
3. 再叠 `status`
4. 最后排序与分页

也就是说，列表入口最好一开始就长成这样：

```go
queryDB := applyDataScope(r.db.Model(&model.User{}), actor)
```

### 这一关通过后，应该看到什么

- 权限边界从查询源头就开始生效
- `Count` 和 `Find` 都在同一条边界上执行
- 业务筛选永远是在权限裁剪后的结果上继续缩小

### 这一步常见失败信号

- 先把全量数据查出来，再在内存里筛
- `Count` 忘记套 Scope，导致分页总数不对
- 列表查了范围，详情或导出没查范围

## 第五关：单条资源查询和写操作前检查是否也复用同一边界

第 5 章最容易漏掉的，不是列表，而是：

- 更新
- 状态切换
- 角色绑定
- 组织关系调整

这些动作真正安全的关键在于：

- 更新前先按同一权限边界查目标资源

所以像用户和部门这种资源，当前更稳的做法是：

- `FindByIDInScope(...)`

### 这一关通过后，应该看到什么

- 列表里看不到的资源，在更新动作里同样查不出来
- “能不能看” 和 “能不能继续操作” 站在同一条边界上

### 这一步常见失败信号

- 列表权限是对的，但知道 ID 后仍能直接改数据
- 更新前用的是普通 `FindByID(...)`
- Handler 按 ID 继续处理时没有再走范围检查

## 第六关：角色手工验收是否真的能跑出差异

最后一关一定要回到真实角色验证。

当前第 5 章的数据权限，不应该只停留在：

- 代码结构看起来像那么回事

而要能通过下面这类测试：

1. `all` 角色用户能看到全量资源
2. `dept` 角色用户只能看到本部门资源
3. `dept_and_children` 用户能看到本部门及子部门资源
4. `custom_dept` 用户能看到授权部门集合
5. `self` 用户只能看到本人或退化资源

### 这一关通过后，应该看到什么

- 同一个接口对不同角色返回结果明显不同
- 超级管理员能稳定绕过数据权限
- 模块没有出现“列表对了、更新错了”的割裂情况

### 这一步常见失败信号

- 页面权限正确，但数据仍然是全量
- `custom_dept` 看不到授权部门，或反而越权
- 多角色用户结果不稳定，表现像“只取了第一个角色”

## 一份可直接复用的验收表

你可以直接按下面这份表核对一个模块：

| 维度 | 要检查什么 | 通过标准 |
| --- | --- | --- |
| 资源边界 | 是否先判断资源与组织体系关系 | 已明确选定 `User / Department / 放开` 三类之一 |
| 请求上下文 | 是否完全依赖统一 `Actor` | 模块不再自己重查角色范围 |
| 模块声明层 | 是否有稳定的 `datascope.go` | 过滤字段集中声明，未散写 |
| Repository | 是否一开始就先套 `applyDataScope(...)` | 列表、总数、排序、分页在同一边界上 |
| 单条资源 | 是否有 `FindByIDInScope(...)` 或等价边界 | 更新、状态切换、关系修改不越界 |
| 手工验证 | 不同角色结果是否真的不同 | `all / dept / custom_dept / self` 行为可验证 |

这份清单更像“最后验收”，不是替代前面的正文说明。  
如果某一关过不去，当前更稳的回看方式是：

## 当前什么时候才算“这个模块真的进入了第 5 章主线”

可以用一句更严格的话来判断：

> 只有当“资源边界、Actor、模块声明层、Repository、单条资源检查、角色验证”六件事同时成立时，这个模块才算真的进入了第 5 章的数据权限主线。

如果只完成了其中两三项，它更像是：

- 数据权限半成品
- 或者只有列表能演示的局部实现

而不是一个后续可以继续复用的稳定模式。
