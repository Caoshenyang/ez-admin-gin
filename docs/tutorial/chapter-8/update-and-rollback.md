# 更新与回滚策略

部署上线之后，真正让人焦虑的通常不是“第一次怎么跑起来”，而是：

> 改完代码再发一版时，怎样更新更稳；如果出了问题，又怎样尽快退回上一版。

这一页就围绕当前仓库已有的真实部署链路，把“更新”和“回滚”拆开讲清楚。

::: tip 🎯 本节目标
读完后，你应该能明确：

1. 当前仓库推荐的更新路径是什么
2. 为什么首次部署和日常更新不能混用同一套脚本
3. 当前没有专门回滚脚本时，怎样做一条足够稳的人工回滚路线
:::

## 先说结论：当前更新主线很简单

当前仓库的推荐更新路径就是：

```text
本地重新打包
  ↓
上传新部署包
  ↓
解压覆盖到 /opt/ez-admin
  ↓
执行 update-server.sh
```

也就是说，后续更新默认不再执行：

- `setup-server.sh`

而是只执行：

- `update-server.sh`

## 为什么日常更新不能再跑 `setup-server.sh`

因为 `setup-server.sh` 的定位一直都是：

- 首次部署脚本

它会处理很多只该做一次的事情，例如：

- `.env.example` 初始化成 `.env`
- JWT 密钥首次替换
- 管理员初始化
- 基础目录准备

如果每次更新都重新跑它，就很容易把“首次部署逻辑”和“版本更新逻辑”混在一起，增加误操作风险。

## `update-server.sh` 当前到底做了什么

当前更新脚本很克制，核心就两件事：

1. 如果有新的前端构建产物，就把 `dist/` 整理成 `web/`
2. 重启 `ez-admin` systemd 服务

这意味着它不会主动去碰：

- 数据库容器
- Redis 容器
- `.env`
- 数据卷
- 管理员初始化

这种设计很符合后台交付的常识：

> 日常更新只替换代码和静态资源，不轻易碰环境与数据。

## 当前推荐的更新顺序

如果你要发一个新版本，建议按下面顺序来：

1. 本地执行 `bash scripts/pack.sh` 或 `.\scripts\pack.ps1`
2. 把新的部署包上传到服务器
3. 先备份当前部署包或当前二进制
4. 解压覆盖到 `/opt/ez-admin`
5. 执行 `sudo bash /opt/ez-admin/update-server.sh`
6. 立刻做最小验收

这里第 3 步虽然不是脚本强制要求，但在真实环境里非常值得保留。

## 更新后最小验收应该看什么

更新成功后，最少建议看下面几项：

1. `sudo systemctl status ez-admin`
2. `docker compose -f /opt/ez-admin/compose.server.yml ps`
3. 浏览器打开后台首页
4. 管理员登录一次
5. 随便打开一个系统页并执行一个轻操作

如果这五步都正常，通常就说明：

- 后端二进制可运行
- 前端静态资源可访问
- API 入口层正常
- 基础容器没被破坏

## 当前回滚为什么还没有独立脚本

因为仓库目前的重点是先把“首版上线”和“日常更新”这两条主线稳定下来。

所以当前并没有提供：

- `rollback-server.sh`

这不代表不能回滚，而是说明当前仓库默认的回滚方式更偏向：

- 保留上一版部署包
- 保留上一版二进制或完整目录
- 出问题时人工切回

## 当前最稳的人工回滚思路

如果你想在现有结构下做一条最稳的人工回滚路线，建议这样做：

### 方案一：保留上一个部署包

每次发版前，把上一版部署包先留一份，例如：

- `deploy-package-2026-04-30.tar.gz`

如果新版本有问题，就：

1. 重新把上一版包解压回 `/opt/ez-admin`
2. 再执行 `sudo bash /opt/ez-admin/update-server.sh`

### 方案二：保留上一个部署目录快照

例如发布前做一次：

```bash
sudo cp -r /opt/ez-admin /opt/ez-admin-backup-2026-04-30
```

如果新版本不稳定，就把：

- `server`
- `web`
- 必要脚本

从旧目录恢复回来，再重启服务。

## 回滚时哪些东西通常不该动

当前结构下，回滚最重要的原则是：

> 优先回滚代码和静态资源，不要轻易回滚数据目录。

也就是说，一般不要直接去回滚：

- `data/postgres`
- `data/redis`
- `.env`

除非你非常明确自己在处理什么。

因为很多“版本有问题”的场景，真正要退回的只是：

- Go 二进制
- 前端静态资源
- Nginx 配置

而不是把数据库也一起倒回去。

## 什么时候回滚会变复杂

有两类更新会让回滚明显变难：

1. 改了数据库迁移
2. 改了配置结构或环境变量约定

这类情况下，单纯换回旧二进制未必足够，因为：

- 数据表结构可能已经变了
- 新旧版本对配置的理解可能不同

更细的判断和动作拆分，可以继续读下一页 [回滚分级策略](./rollback-strategy-levels)。

## 一份当前结构下的快速回滚清单

如果你现在就要基于当前仓库落地一条最低成本回滚策略，可以直接照下面做：

1. 每次发版都保留一个版本化部署包
2. 更新前先留一份 `/opt/ez-admin` 快照
3. 只要不是数据迁移类问题，优先回滚 `server + web`
4. 回滚后重新执行 `sudo bash /opt/ez-admin/update-server.sh`
5. 立刻做登录、菜单、系统页最小验收
