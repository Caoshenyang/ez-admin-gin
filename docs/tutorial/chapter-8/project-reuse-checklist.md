# 新项目复用清单

本章最后要回答的问题，不是”怎么把这一个项目部署出去”，而是：

> 如果我要基于这套底座再开一个新项目，应该从哪里开始复用。

这一页就是把“复制仓库开新项目”这件事，拆成一份更稳的清单。

::: tip 🎯 本节目标
读完后，你应该能更清楚地判断：

1. 哪些东西应该直接保留
2. 哪些东西必须优先替换
3. 哪些东西应该等业务主线稳定后再补
:::

## 先说最重要的判断

当前仓库最值得复用的，从来都不只是某几个页面或几个 SQL 文件，而是整套分层结构：

```text
server: bootstrap / platform / module
admin: api / layouts / pages / router / types / utils
docs: tutorial / guide / reference
deploy: compose / nginx / service / env
scripts: pack / setup / update
```

所以新项目复用时，真正应该保留的核心是：

- 工程结构
- 权限体系
- 数据权限主线
- 部署链路

而不是只复制一个“后台皮肤”。

## 哪些内容通常应该直接保留

如果你是基于它起一个新后台项目，下面这些一般都值得优先原样保留：

### 后端基础设施

- `bootstrap`
- `platform/config`
- `platform/database`
- `platform/logger`
- `platform/redis`
- `platform/authn`
- `platform/authz`
- `platform/datascope`

### 管理后台基础层

- 登录页主链路
- 后台壳子
- 动态菜单机制
- 按钮权限消费方式
- 系统页面模式

### 部署链路

- `pack.sh / pack.ps1`
- `setup-server.sh`
- `update-server.sh`
- `compose.server.yml`
- `ez-admin.service`

这些内容的共同点是：

- 和具体业务领域弱耦合
- 已经被当前仓库反复收口过
- 对新项目起步帮助最大

## 哪些内容应该优先替换

新项目一开始最该优先改的，通常不是代码行数最多的地方，而是“项目身份信息”。

建议优先替换：

1. 仓库名和模块名
2. `go.mod` 里的模块路径
3. 文档标题、说明和品牌文案
4. 登录页、Logo、后台标题里的项目名称
5. 默认环境变量模板和域名相关说明

如果这些不先改，后面越往下做，旧项目痕迹会越难清理。

## 后端模块复用时，什么最值得参考

当前最适合被新项目复用的模块模板，不是“所有模块都照搬”，而是优先看：

- 用户模块：看标准管理页和数据权限接入
- 角色 / 菜单模块：看权限体系
- 公告模块：看轻量内容资源
- 配置 / 文件模块：看基础能力资源

也就是说，新项目不一定要把当前所有 `system` 模块都带上，但非常值得把它们当作：

> 不同类型模块的样板。

## 前端复用时，最该保留什么

新项目里前端最不该推倒重来的是：

- `router/index.ts`
- `dynamic-menu.ts`
- `AdminLayout.vue`
- `utils/auth.ts`
- 系统页面骨架模式

因为这几层一旦保住，你后面接业务页时的心智会非常稳定：

- 页面怎么进后台
- 菜单怎么注册
- 按钮怎么显隐
- 登录态怎么流转

都会继续沿用同一套结构。

## 哪些系统模块要“保留但延后裁剪”

有些模块虽然不是每个项目都马上用得上，但我更建议先保留、后面再裁：

- 登录日志
- 操作日志
- 文件管理
- 系统配置

原因很简单：这些能力很多时候在项目初期看起来“不急”，但一到联调、排障、上线就会发现非常有用。

## 什么时候应该开始删减

更稳的做法通常不是“起项目第一天就大删特删”，而是：

1. 先把新业务主线跑起来
2. 再决定哪些系统模块真的不需要
3. 最后再做有意识的裁剪

这样你就不会因为删太早，后面又被迫把日志、上传、配置这些基础能力补回来。

## 一个最实际的复用顺序建议

如果你明天就要基于这套底座开新项目，我会更推荐按下面顺序做：

1. 复制仓库
2. 改项目身份信息与模块路径
3. 跑通本地后端、前端、文档和部署构建
4. 保留当前权限、菜单、用户和基础系统模块
5. 新增你的第一个真实业务模块
6. 再决定是否裁掉暂时不用的系统能力

这条顺序的核心在于：

> 先让底座继续工作，再做个性化收缩。

## 一份可直接执行的复用清单

你可以直接按下面这份清单逐项做：

1. 复制仓库到新目录
2. 替换 `server/go.mod` 模块名和 Go import 路径
3. 替换前端品牌名、Logo 和文档标题
4. 重新检查 `deploy/.env.example`、服务名和部署目录命名
5. 运行后端、前端、文档构建，确认底座没有被改坏
6. 保留 `auth / iam / system` 主链路，新增你的第一个业务模块
7. 补你的业务菜单、按钮权限和前端页面映射
8. 最后再决定是否裁掉部分默认系统能力

## 什么时候这套底座就算“复用成功”

不是“仓库名改掉了”就算成功，而是：

- 登录能跑
- 菜单能出
- 权限能控
- 数据范围能复用
- 部署脚本还能发版

当这些都还成立时，你才是真的把它复用成了一个新项目底座，而不是复制了一堆看起来很像的代码。
