# 数据字典模块落地

::: info 扩展阅读定位
这页保留为第 8 章的扩展实现参考，用来补充“系统级公共模块”如何按同一套骨架落地。当前 canonical 主线仍然以 [CRM 客户模块示例](./business-module-example) 为唯一完整案例。
:::

前面第 8 章已经把“新模块怎么接进后台底座”讲成了一条固定顺序。现在进入 `Phase 4` 后，最值得先补的第一个真实模块，就是数据字典。

::: tip 🎯 本节目标
读完这一节，你应该能看清三件事：

- 为什么数据字典适合作为 `Phase 4` 的第一个模块
- 为什么它会采用“字典类型 + 字典项”两张表，但仍然只落成一个 `system/dict` 模块
- 这类系统级公共字典为什么默认不进入第 5 章的数据权限裁剪
:::

## 为什么先做数据字典

数据字典很适合当 `Phase 4` 的起点，因为它刚好踩在两条主线的交叉点上：

- 它已经是真实交付模块，不再只是教程示例
- 它又不需要一开始就引入复杂流程、跨模块事务或部门级数据权限

也就是说，它足够像一个项目里真的会交付的系统级模块，但不会让第一步就掉进高复杂度业务。

## 当前实现怎么切模块边界

这次数据字典没有拆成两个后端模块，而是只保留一个：

```text
server/internal/module/system/dict/
├─ dto.go
├─ entity.go
├─ repository.go
├─ service.go
├─ handler.go
├─ routes.go
└─ policy.go
```

但它内部同时管理两类实体：

- `sys_dict_type`
- `sys_dict_item`

这样做的原因很直接：

- 字典类型和字典项总是一起出现
- 前端管理台也会在一页里联动维护它们
- 权限、菜单、默认种子和测试链路都更适合作为一个完整模块交付

## 为什么不是一张表

如果把数据字典压成一张表，很快就会遇到两个问题：

1. 没法稳定表达“先有类型，再有项”
2. 同一个字典项编码在不同类型下是否允许重复，会变得难以约束

所以当前实现直接固定为“两张表 + 一个模块”：

```text
sys_dict_type
  ↓
sys_dict_item.type_id
```

这里不建数据库外键，只靠：

- `type_id`
- 联合唯一索引 `(type_id, item_key)`
- service 层存在性校验

来维持关系，这和当前整套后台底座的关系约束方式保持一致。

## 这次补了哪些后端接口

当前数据字典模块先补的是最稳的一组后台管理接口：

### 字典类型

- `GET /api/v1/system/dict-types`
- `POST /api/v1/system/dict-types`
- `POST /api/v1/system/dict-types/:id/update`
- `POST /api/v1/system/dict-types/:id/status`

### 字典项

- `GET /api/v1/system/dict-items`
- `POST /api/v1/system/dict-items`
- `POST /api/v1/system/dict-items/:id/update`
- `POST /api/v1/system/dict-items/:id/status`

这里刻意没有先补删除接口，原因和公告、配置模块保持一致：

- 先把“创建 / 编辑 / 状态切换 / 列表查询”这条主线做稳
- 删除策略、是否允许复用编码、删类型时如何处理子项，留到后续需求真的出现时再扩

## 权限和菜单为什么要一起补

数据字典不是“后端先有接口，页面后面再说”的模块。

这次它和代码一起补齐了四件事：

1. `policy.go` 权限常量
2. `casbin_rule` 默认接口授权
3. `sys_menu` 菜单与按钮节点
4. `sys_role_menu` 超级管理员默认可见

也就是说，一个全新的系统模块，只要真的要进入后台管理台，就不应该把权限和菜单留成“后续手工配置”。

## 前端这一页为什么做成双表

当前前端页面是：

```text
admin/src/pages/system/DictView.vue
```

它没有拆成“类型页”和“字典项页”两张页面，而是用一页双表来承接：

- 上半区维护字典类型
- 下半区维护当前选中类型下的字典项

这种做法更适合数据字典，因为它天然是“父子关系强联动”的资源：

- 维护字典项时，总要知道自己现在挂在哪个类型下
- 维护字典类型时，又经常马上就要继续补它的字典项

所以当前实现不是把页面拆得更细，而是让这类资源在一屏里完成上下文切换。

## 为什么它默认不接数据权限

第 5 章已经讲过：不是每个模块都应该直接套 `department` 或 `user` 级数据权限。

数据字典当前更接近：

> 系统级公共字典

因此这次实现明确采用“当前显式放开”的模式：

- 没有 `datascope.go`
- 不按部门过滤
- 不按用户归属过滤

这不是遗漏，而是有意识的边界判断。只有等后续真的出现“租户级字典”“部门私有字典”这类需求时，才值得把它从系统公共资源演进成更细的数据权限资源。

## 这次种了什么初始化数据

为了让模块一落地就能看到真实效果，这次默认种了两类内容：

### 示例字典类型与字典项

- `common:yes-no`
- `notice:level`

### 后台菜单与按钮

- `system:dict`
- `system:dict:type:*`
- `system:dict:item:*`

这让数据字典不只是“代码存在”，而是可以直接在后台打开、查看和继续编辑。

## 这个模块和第 8 章前几页是什么关系

如果把前几页看成规范，那么数据字典就是第一个正式按规范交付出来的 `Phase 4` 模块。

它验证了下面这条链已经成立：

```text
两张真实业务表
  ↓
一个稳定模块目录
  ↓
聚合路由注册
  ↓
Casbin / 菜单 / 按钮 / 默认授权
  ↓
前端 api / types / page / dynamic-menu
  ↓
自动化测试基线覆盖一条成功路径
```

这一步完成后，后面的账户中心、附件中心和非 `system` 分组业务示例，就不再需要重新讨论“模块应该怎么长”，而是直接沿着这条链扩。

## 本节最关键的结论

数据字典这次不是一个“补功能点”，而是 `Phase 4` 真正开始的标志。

它说明当前底座已经能从：

- 平台骨架
- 权限体系
- 数据权限
- 系统模块
- 前端管理台
