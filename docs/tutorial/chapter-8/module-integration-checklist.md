# 模块接入验收清单

前面几页已经分别讲了：

- 后端模块应该怎么落目录
- 权限、菜单和迁移应该怎么接
- 前端页面应该怎么接进动态菜单

但真实项目里，最容易出问题的往往不是“不会新增文件”，而是：

> 文件都加了，页面也能打开了，可这个模块其实还没有真正进入系统。

所以这一页专门回答一个更实际的问题：

> 一个新模块，到底满足什么条件，才算接入完成。

::: tip 🎯 本节目标
读完后，你应该能拿这份清单去验收一个新模块，而不是只判断“代码看起来差不多写完了”。
:::

## 先给结论：模块接入完成至少要过五关

在当前最终版结构里，一个模块真正接入完成，至少要同时满足下面五件事：

1. 后端模块已经进入固定结构，并能稳定提供接口
2. 菜单、按钮权限和 Casbin 种子已经和模块代码一起落地
3. 前端页面已经接进动态菜单和动态路由
4. 需要数据权限的资源，已经接入 Actor 和查询作用域链路
5. 关键操作已经能被手动验证，而不是停留在“理论上应该可用”

也就是说，判断标准不是“有没有这个模块目录”，而是：

```text
后端能提供
  ↓
权限能控制
  ↓
前端能进入
  ↓
数据能过滤
  ↓
操作能验证
```

## 第一关：后端模块结构是否成立

先检查模块本身是不是已经按当前主线落进固定结构。

最基础的检查项是：

- 是否已经进入 `server/internal/module/<group>/<module>/`
- 是否至少具备 `dto / entity / repository / service / handler / routes`
- 如果模块有权限点，是否补了 `policy.go`
- 如果模块有资源级数据过滤，是否补了 `datascope.go`
- 是否已经接入对应的上层聚合路由，例如 `module/system/routes.go`

### 这一关通过后，应该看到什么

- 接口路径已经能在统一分组下访问，例如 `/api/v1/system/*`
- 模块不是靠改全局散装路由临时接进去
- Handler 不直接承担数据库查询与业务编排

### 这一步常见失败信号

- 模块虽然存在，但没有被上层 `routes.go` 注册
- 业务逻辑还堆在 Handler 里，没有真正沉到 `service / repository`
- 权限常量散落在多个文件里，没有稳定落点

## 第二关：菜单、按钮和接口权限是否闭环

当前系统里，一个模块接进后台，不只是把接口开放出来，还要把权限链路一起补齐。

至少要检查下面几项：

- `policy.go` 里是否已经声明模块自己的权限码
- `casbin_rule` 初始化数据是否已经包含接口权限
- `sys_menu` 初始化数据是否已经包含菜单节点
- 页面里的按钮操作，是否已经补了按钮权限节点
- `sys_role_menu` 这条授权链路是否能把页面入口和按钮权限一起发给前端

::: warning ⚠️ 这里最容易漏的是按钮权限节点
很多模块在这一步只补了页面菜单节点，结果登录后页面能打开，但“新增、编辑、删除、状态切换”这些按钮全都不显示。

原因不是前端样式问题，而是按钮权限节点根本没有进入菜单树。
:::

### 这一关通过后，应该看到什么

- 角色授权后，用户能在侧边栏看到页面入口
- 页面内按钮显隐能跟着权限变化
- 未授权接口会被 `middleware.Permission` 稳定拦截

### 这一步常见失败信号

- 数据库里 `component` 已经写了，但前端仍然打开占位页
- 页面入口可见，但按钮一直不显示
- 角色刚改完权限后，接口行为和预期不一致

::: details 为什么“角色改完权限后还不生效”偶尔会出现？
当前实现里，Casbin 策略在服务启动时加载，角色接口权限改完后不会自动热刷新。

所以如果你修改的是接口权限，而不是菜单显示，现阶段更稳的验证方式仍然是重启后端服务再复测一次。
:::

## 第三关：前端页面是否真正进入动态菜单链路

当前前端不是手写一张静态业务路由表，而是依赖：

- `/api/v1/auth/menus`
- `admin/src/router/dynamic-menu.ts`

来生成侧边栏和页面路由。

所以前端这一步至少要核对：

- `admin/src/types/<module>.ts` 是否已经补好
- `admin/src/api/<module>.ts` 是否已经围绕资源接口封装完成
- `admin/src/pages/<group>/<Module>View.vue` 是否已经实现页面
- `dynamic-menu.ts` 里的 `routeComponentMap` 是否已经加入对应组件 key
- 后端 `sys_menu.component` 是否和 `routeComponentMap` key 完全一致

### 这一关通过后，应该看到什么

- 登录后菜单里能出现新页面
- 点击菜单能进入真实页面，而不是落到 `PagePlaceholder`
- 页面请求能正常走统一鉴权链路，不需要页面自己拼 `Authorization`

### 这一步常见失败信号

- 菜单出现了，但点击后进入空白占位页
- 页面文件存在，但动态菜单映射没有补
- 页面里直接手写请求细节，没有复用 `api/http.ts`

## 第四关：需要数据权限的模块，是否真的接了查询过滤

不是所有模块都需要数据权限，但只要资源和“谁能看到哪些数据”相关，这一关就不能跳过。

至少要检查：

- 请求链路是否已经经过 `middleware.LoadActor`
- 模块是否定义了自己的资源级 `datascope.go`
- 查询是否通过 `gorm.Scopes(...)` 接入过滤
- 多角色并集、超级管理员放行、空范围默认拒绝等规则是否符合当前主线

这一步特别适用于：

- 用户
- 部门
- 岗位
- 以及未来非 `system` 分组下的真实业务模块

### 这一关通过后，应该看到什么

- 不同角色登录后，同一个列表接口返回结果有差异
- 超级管理员能看到全量数据
- 自定义部门范围角色不会越权读到无关资源

### 这一步常见失败信号

- 页面权限已经生效，但列表仍然返回全量数据
- 只有 Handler 判断角色，没有把过滤沉到查询作用域
- 多角色用户结果不稳定，出现“取第一个角色”的临时写法

## 第五关：关键操作是否完成了最小手工验收

模块真正接入完成前，至少要做一轮最小手工验证。推荐按下面顺序过一遍：

1. 用有权限账号登录，确认菜单出现
2. 进入页面，确认列表接口正常返回
3. 走一遍新增或编辑，确认写操作成功
4. 刷新页面，确认数据不是只在前端假更新
5. 用低权限账号复测，确认页面入口、按钮和数据范围都符合预期

## 一份可直接复用的验收清单

你可以直接按下面这份清单逐项核对：

| 维度 | 要检查什么 | 通过标准 |
| --- | --- | --- |
| 后端结构 | 模块是否进入固定目录与固定分层 | 目录稳定、路由已注册、职责清晰 |
| 接口权限 | Casbin 权限是否补齐 | 授权后可访问，未授权被拦截 |
| 菜单权限 | 页面节点和按钮节点是否都存在 | 页面可见，按钮显隐正确 |
| 前端接入 | 类型、API、页面、动态映射是否齐全 | 菜单能开页，不落占位页 |
| 数据权限 | 是否接入 Actor + Scopes | 不同角色看到不同数据 |
| 手工验证 | 是否完成最小闭环测试 | 登录、查询、写入、复测都通过 |

## 当前主线下，什么时候才能说“模块真的进入后台了”

可以用一句更严格的话来判断：

> 只有当“接口、权限、菜单、页面、数据范围、验证结果”六件事都成立时，这个模块才算真正进入当前后台底座。

如果只完成了其中两三项，它更像是：

- 后端半成品
- 前端半成品
- 或者只能本地演示的开发中模块

而不是一个可以继续复用的企业级底座能力。
