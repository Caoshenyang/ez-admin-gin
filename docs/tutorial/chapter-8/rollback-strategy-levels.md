# 回滚分级策略

前一页已经把“怎么更新、怎么做最低成本回滚”讲清楚了，但真实交付里更关键的问题通常是：

> 这次故障到底属于哪一级，我应该回滚到什么程度，哪些东西绝对不能乱动。

如果这里判断错了，就很容易出现两种极端：

- 明明只是前端资源问题，却把数据库一起折腾了
- 明明已经动到迁移和配置边界，却还在按“换回二进制就行”处理

这一页的目标，就是把当前底座里的回滚动作拆成一套能执行的分级策略。

::: tip 🎯 本节目标
读完后，你应该能判断：

1. 哪些故障只需要回滚 `server + web`
2. 哪些故障已经进入“配置变更”级别
3. 哪些故障必须把数据库迁移、初始化数据和版本兼容一起评估
:::

## 先记住当前回滚边界

当前本章默认主线里，最常见的可回滚对象有四类：

| 对象 | 典型内容 | 风险等级 |
| --- | --- | --- |
| 前端静态资源 | `/opt/ez-admin/web` | 低 |
| 后端二进制 | `/opt/ez-admin/server` | 低到中 |
| 入口层配置 | `nginx-native.conf`、`nginx-native-ssl.conf`、systemd 服务配置 | 中 |
| 数据与配置边界 | `.env`、数据库迁移、初始化数据 | 高 |

真正需要分级的核心原因是：

- 越靠近数据和配置，回滚代价越高
- 越靠近页面和二进制，回滚动作越容易做到“只换文件”

## Level 1：只回滚页面或二进制

这一层是最常见、也最适合快速处理的一层。

### 典型症状

- 首页样式错乱
- 某个系统页白屏
- 前端按钮显隐异常
- 某个接口版本发出去后立刻报错
- 更新后服务能启动，但业务行为明显不对

### 当前推荐动作

优先回滚：

- `/opt/ez-admin/web`
- `/opt/ez-admin/server`

然后重新执行：

```bash
sudo bash /opt/ez-admin/update-server.sh
```

### 为什么这一层最适合快回滚

因为它通常不涉及：

- 数据结构变化
- 环境变量变化
- 初始化脚本行为变化

所以这类问题本质上更像：

> 发布包内容回退，而不是环境回退。

## Level 2：入口层与部署配置回滚

这一层的问题，通常已经不只是业务代码，而是部署边界本身受影响了。

### 典型症状

- 首页能打开，但 `/api/*` 全部 502
- 刷新路由后直接 404
- HTTPS 配置切换后站点不可访问
- 文件上传突然全部失败
- 后端服务本身正常，但公网入口层行为异常

### 当前推荐动作

先回滚：

- Nginx 配置
- 必要时回滚 `ez-admin.service`
- 再决定是否一起回滚 `server + web`

排查顺序建议是：

1. 先确认是不是入口层配置变了
2. 再确认是不是后端二进制一起变了
3. 最后才考虑是不是容器和网络结构变了

### 为什么这一层不能只盯着业务代码

因为这类问题的根因往往在：

- `proxy_pass`
- `try_files`
- `client_max_body_size`
- SSL 证书路径
- `systemd` 启动参数或工作目录

这类问题如果只换回业务包，未必能恢复。

## Level 3：环境变量与配置结构回滚

这一层已经比“入口层异常”更敏感，因为它涉及：

- `.env`
- 配置读取逻辑
- 新旧版本的配置兼容关系

### 典型症状

- 更新后服务启动失败，但二进制本身并没有坏
- 日志里出现缺失配置、配置解析失败、连接参数错误
- 数据库或 Redis 连接突然异常
- 登录、签权、上传等链路同时出现系统性问题

### 当前推荐动作

不要急着整体回退数据，先做三步：

1. 对比新旧版本 `.env` 和配置读取约定
2. 判断是不是新增了必填环境变量
3. 确认旧版本是否还能正确理解当前 `.env`

如果确认问题在配置层，再回滚：

- `.env`
- 相关 systemd / Nginx 配置
- 必要时再配合回滚 `server`

### 这一层最容易犯的错

最容易犯的错是：

> 看到服务起不来，就立刻把整个部署目录一把切回去。

如果新旧版本共用同一个数据目录，而你又没有先确认配置兼容，粗暴切回很可能只会制造第二轮问题。

## Level 4：数据库迁移与初始化数据回滚

这是当前最重的一层，也应该被视为：

> 不到必要时不要轻易触发的回滚层级。

### 典型症状

- 新版本执行迁移后，旧版本读写数据报错
- 某些表字段、索引或约束已经变化
- 初始化数据逻辑改了权限码、菜单结构或系统关键字典
- 旧版本逻辑已经无法兼容新数据形态

### 当前推荐动作

遇到这一层，不要先做“秒级回滚”，而是先做影响面判断：

1. 迁移改了什么
2. 旧版本是否还能读当前表结构
3. 初始化数据是否覆盖了关键权限或菜单
4. 有没有最近的数据备份或快照

只有把这些问题确认清楚，才决定后续动作：

- 是否只回滚应用层版本
- 是否需要补兼容脚本
- 是否需要数据库级恢复

### 为什么这一层要最谨慎

因为数据库回滚不是“换一个文件”。

一旦数据已经被新版本写入，旧版本能不能继续消费它，取决于：

- 表结构兼容性
- 业务约束兼容性
- 初始化数据是否可逆

所以这类问题更像一次小型变更应急，而不是普通回滚。

## 一张分级决策表

| 现象 | 优先判断级别 | 第一动作 |
| --- | --- | --- |
| 页面白屏、样式错乱、轻量接口异常 | Level 1 | 回滚 `web` / `server` |
| 502、404、HTTPS 切换失败、上传失败 | Level 2 | 回滚入口层配置 |
| 服务起不来、连接参数异常、签权链路系统性失效 | Level 3 | 对比 `.env` 与配置结构 |
| 迁移后旧版本读写报错、菜单权限体系被改坏 | Level 4 | 停止快回滚，先做兼容与数据评估 |

## 当前底座的推荐回滚顺序

如果你还拿不准问题落在哪层，可以按下面顺序往上加码，而不是一开始就做最大动作：

1. 先尝试 Level 1：只回滚 `server + web`
2. 不行再进入 Level 2：检查并回滚 Nginx / systemd 边界
3. 再判断是否进入 Level 3：配置与环境变量兼容问题
4. 只有确认涉及迁移或初始化数据，才进入 Level 4

这条顺序的核心价值在于：

> 先用最小动作恢复可用，再决定是否需要更重的回退。

## 发版前怎么降低高等级回滚概率

如果你想让回滚尽量停留在 Level 1 或 Level 2，发版前最值得做的是：

1. 保留版本化部署包
2. 保留 `/opt/ez-admin` 快照
3. 记录这次发版是否包含迁移、配置变更、初始化数据调整
4. 在上线前先跑最小验收链路
5. 对高风险发布单独标记“可能进入 Level 3/4”

这样真正出问题时，你不会一边排查一边猜：

- 这次到底动没动迁移
- 这次有没有加环境变量
- 这次能不能直接换回上一版
