# 长期运维 FAQ

本章前面几页主要解决三件事：

- 怎么把项目部署上去
- 出问题时先怎么排障
- 需要回滚时该回滚到什么程度

但系统一旦上线，真正持续消耗精力的往往不是“第一次部署”，而是这些重复动作：

> 平时看什么、多久检查一次、日志怎么查、备份怎么留、证书怎么换、发版前后要不要固定做一套动作。

这一页就把这些更偏“长期维护”的动作集中整理成 FAQ。

::: tip 🎯 本节目标
读完后，你应该能建立一套最小但稳定的运维节奏，而不是每次都临时想“现在该看什么命令”。
:::

## 先建立一套最小维护节奏

如果你现在只有一个人或一个很小的团队在维护这套后台，先不用追求复杂监控系统，先把下面这套节奏固定下来就够有价值：

| 频率 | 最值得做的事 |
| --- | --- |
| 每次发版前后 | 跑一遍最小验收，确认登录、菜单、系统页、日志链路正常 |
| 每天或每次登录服务器时 | 看 `systemctl status`、`docker compose ps`、磁盘空间 |
| 每周 | 看日志增长、备份结果、证书有效期 |
| 每月 | 复查 `.env`、备份保留策略、上传目录和数据库体积 |

这套节奏的关键不是“全做得很重”，而是：

> 让关键动作有固定节拍，减少纯靠记忆维持系统的风险。

## Q1：平时最值得先看的三个命令是什么？

如果你只记住三条日常命令，优先记下面这组：

```bash
sudo systemctl status ez-admin
docker compose -f /opt/ez-admin/compose.server.yml ps
df -h
```

它们分别回答三个最基本的问题：

- 后端服务在不在
- 基础容器在不在
- 服务器磁盘还够不够

对当前这套结构来说，这三件事比“先看业务功能页”更适合作为日常巡检入口。

## Q2：日志平时应该怎么查？

当前默认主线里，日志要分两层看：

### 后端服务日志

先看：

```bash
sudo journalctl -u ez-admin -n 200
sudo journalctl -u ez-admin -f
```

适合排查：

- 启动失败
- 配置读取异常
- 数据库 / Redis 连接问题
- 业务接口运行报错

### 容器层日志

先看：

```bash
docker compose -f /opt/ez-admin/compose.server.yml logs postgres
docker compose -f /opt/ez-admin/compose.server.yml logs redis
docker compose -f /opt/ez-admin/compose.server.yml logs nginx
```

适合排查：

- PostgreSQL / Redis 容器重启
- Nginx 入口层问题
- SSL 配置切换异常

### 为什么要强行分两层

因为当前后端不在 Docker 里。

如果你一看到报错就只去翻 Compose 日志，很容易漏掉真正的后端错误；反过来，如果入口层出了问题，只盯 `journalctl` 也会看偏。

## Q3：需要长期保留哪些业务侧审计信息？

除了系统层日志，当前后台还内置了两类特别值得长期观察的页面：

- 登录日志
- 操作日志

它们和 `journalctl` 不一样，回答的是：

- 谁登录了系统
- 谁改了什么资源

所以当你遇到“是不是最近有人改过角色权限”“是不是某个账号频繁登录失败”这类问题时，更应该先看后台里的日志页，而不是只看服务器控制台。

## Q4：备份最少应该覆盖哪些内容？

对当前默认部署主线来说，最小备份集合通常至少包括：

1. PostgreSQL 数据
2. `.env`
3. `/opt/ez-admin/web`
4. `/opt/ez-admin/server`
5. `/opt/ez-admin/nginx/`
6. `/opt/ez-admin/ssl/`
7. 上传文件目录（如果业务真的在用）

### 为什么 `.env` 也要进备份

因为它不只是几个变量，而是当前部署环境的真实身份信息：

- JWT 密钥
- 数据库连接信息
- Redis 密码
- 可能还有未来新增的关键环境变量

代码可以重拉，`.env` 丢了以后，恢复成本往往比想象中高。

## Q5：数据库备份平时怎么做比较稳？

如果你还没有更重的数据库备份体系，当前最实用的最低配做法是：

```bash
docker compose -f /opt/ez-admin/compose.server.yml exec -T postgres \
  pg_dump -U ez_admin ez_admin > /opt/ez-admin/backup-$(date +%F).sql
```

这条命令的价值在于：

- 不需要对外开放数据库端口
- 直接在当前容器环境里导出
- 可以先做成最基础的手工备份或定时任务

::: warning ⚠️ 先确认用户名和库名
如果你的 `.env` 已经改过数据库用户名或数据库名，记得同步替换 `pg_dump` 里的 `-U` 和库名，不要直接照抄默认值。
:::

## Q6：上传文件和数据库，哪个更容易被漏备份？

在后台系统里，最容易被漏掉的通常不是数据库，而是：

- 上传文件
- SSL 证书
- `.env`

因为很多人会自然想到“数据库要备份”，却忘了：

- 文件元数据在数据库里
- 文件内容在磁盘里

如果只还原数据库，不还原上传目录，最后看到的就会是：

- 列表里有文件记录
- 但点开全是 404

## Q7：磁盘空间平时怎么查更有效？

除了 `df -h`，当前更建议配合看两类目录：

```bash
du -sh /opt/ez-admin/data/*
du -sh /opt/ez-admin/web /opt/ez-admin/uploads /opt/ez-admin/ssl 2>/dev/null
docker system df
```

这几条更容易帮助你判断：

- PostgreSQL 数据是不是长太快
- Redis AOF 文件是不是异常膨胀
- 上传文件是不是持续吃盘
- Docker 镜像和层缓存是不是在堆积

## Q8：证书平时怎么维护？

如果当前是按本章主线使用 Cloudflare 源站证书，平时至少要固定看两件事：

1. 证书文件是否仍在 `/opt/ez-admin/ssl/`
2. Nginx 当前是否真的使用了 SSL 配置文件

如果你换证书，建议固定按下面顺序做：

1. 先替换 `cert.pem` / `key.pem`
2. 先做 `nginx -t`
3. 再重载 Nginx
4. 最后浏览器验证 HTTPS 和后台登录

这样能避免最常见的“证书替换了，但入口层没切干净”。

## Q9：平时怎么安全查看线上数据库？

当前数据库和 Redis 都只监听 `127.0.0.1`，这是好事，不建议为了方便而直接对公网开放。

如果你需要临时查数据，更推荐直接走：

- [SSH 隧道连接服务器数据库](../../reference/ssh-tunnel-database)

这样你既能用熟悉的数据库工具查数据，也不会把数据库暴露成公网服务。

## Q10：发版前最值得固定做哪些动作？

如果你想把运维风险尽量压低，发版前建议固定做下面这组动作：

1. 确认这次是否包含数据库迁移
2. 确认这次是否新增了环境变量
3. 保留上一版部署包
4. 保留一份 `/opt/ez-admin` 快照
5. 记录这次是否改了 Nginx / SSL / systemd 配置

这组动作看起来很朴素，但价值很高，因为它们直接决定了：

- 出问题时你能不能快速判断回滚等级
- 旧版本能不能直接切回

## Q11：发版后最小巡检应该怎么做？

当前更推荐一套固定的发版后最小巡检顺序：

1. `sudo systemctl status ez-admin`
2. `docker compose -f /opt/ez-admin/compose.server.yml ps`
3. 打开首页
4. 登录后台
5. 打开一个系统页
6. 看一次操作日志和登录日志
7. 如果用了 HTTPS，再额外验证一次证书和上传接口

这套顺序的好处是，它同时覆盖了：

- 后端存活
- 容器存活
- 页面入口
- 登录链路
- 核心系统页
- 审计链路

## Q12：什么时候应该从“手工运维”升级成更正式的运维体系？

如果开始出现下面这些信号，就说明当前这套最小维护方式快到边界了：

- 发布频率明显升高
- 需要多人轮流值守
- 数据量开始明显增长
- 证书、备份、巡检全靠人记
- 线上故障恢复越来越依赖经验而不是固定流程

这时下一步更值得投入的是：

- 自动备份
- 备份校验
- 基础监控与告警
- 发版记录和变更记录
- 更标准化的回滚演练

## 一份最小长期维护清单

如果你想把这一页直接落成团队动作，可以先固定下面这份清单：

1. 每次发版前记录“是否含迁移 / 配置变更 / 入口层变更”
2. 每次发版后跑一遍最小巡检
3. 每周至少做一次数据库备份检查
4. 每周看一次磁盘占用和日志增长
5. 每月复查一次证书、上传目录、数据库体积和保留策略
