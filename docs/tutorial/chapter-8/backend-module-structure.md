# 后端模块固定结构

第 8 章不再只是回顾第 6 章，而是要回答一个更直接的问题：

> 当你准备新增一个真实业务模块时，后端第一步到底应该长成什么样？

::: tip 🎯 本节目标
读完后，你应该能直接判断：

- 一个新模块最少要建哪些文件
- 哪些文件是默认必备，哪些是按需补充
- 为什么当前主线不再推荐把新模块继续塞回旧的全局 Handler 目录
:::

## 先看当前最小骨架

在当前最终版结构里，一个成熟模块最常见的最小骨架是：

```text
server/internal/module/<group>/<resource>/
├─ dto.go
├─ entity.go
├─ repository.go
├─ service.go
├─ handler.go
├─ routes.go
├─ policy.go
└─ datascope.go
```

但不是每个模块都必须一次补齐全部文件。

## 哪些文件默认必备

一个模块只要准备正式进入后台系统，默认应该先补：

- `dto.go`
- `repository.go`
- `service.go`
- `handler.go`
- `routes.go`
- `policy.go`

这六个文件基本对应了：

- 协议边界
- 数据访问
- 业务编排
- HTTP 入口
- 模块装配
- 权限常量

## 哪些文件按需补

### `entity.go`

适合：

- 想把模块主实体局部别名化
- 后续可能需要把持久化模型和模块实体进一步分开

### `datascope.go`

适合：

- 这个模块需要进入第 5 章的数据权限主线
- 列表、详情或更新前检查都要按当前登录人的组织范围收紧

## 每层最核心的职责

| 文件 | 当前最核心职责 |
| --- | --- |
| `dto.go` | 请求 / 响应结构与参数归一化 |
| `repository.go` | 查询拼装与持久化 |
| `service.go` | 业务规则与事务边界 |
| `handler.go` | HTTP 协议层 |
| `routes.go` | 模块依赖装配与路由注册 |
| `policy.go` | 权限点常量收口 |
| `datascope.go` | 资源级数据权限声明 |

## 为什么这套结构是第 8 章的起点

因为第 8 章讲的是“新模块怎样进入后台底座”，而不是“已有模块长什么样”。

也就是说，第 6 章更多是在证明：

- 当前系统模块已经按最终结构落地

第 8 章则更进一步回答：

- 你接下来的模块，也必须先进入这套结构，后面的权限、菜单、前端接入才有稳定落点

## 最常见的 3 个起步错误

### 1. 先写页面，后补后端结构

这样最容易出现：

- 前端能演示
- 后端接口是临时拼出来的
- 后续补权限和数据权限时返工很重

### 2. 把查询、事务和响应都堆在 Handler

这会让模块一旦稍微变复杂，就很难继续接：

- 缓存同步
- 数据权限
- 多步骤事务

### 3. 一开始就忽略 `policy.go`

这样后面补菜单按钮和 Casbin 种子时，权限点会散在：

- 页面常量
- SQL 种子
- 后端字符串字面量

最终很难稳定维护。

## 本节最短结论

第 8 章里，后端模块起步最稳的顺序不是：

> 先把功能写出来，再回头整理结构

而是：

> 先进入固定骨架，再继续往权限、菜单、前端和数据权限方向扩。
