# 附件中心落地

数据字典和账户中心之后，第 8 章继续补的下一个 `Phase 4` 模块，是附件中心。

它看起来和现有“文件管理”很接近，但这次要解决的问题并不是“再做一套上传页”，而是：

> 当底层上传记录已经存在后，怎样把它提升成可分类、可检索、可业务引用的统一附件资源。

## 这页真正要解决什么

当前仓库里已经有 `system/file` 模块，它负责：

- 校验上传文件
- 生成落盘文件名
- 把文件保存到磁盘
- 把元数据写入 `sys_file`

这个能力已经够做“底层上传服务”了，但还不够支撑真正的附件中心。

因为真实项目里，附件通常还要补这些语义：

- 这份附件在业务上叫什么
- 它属于什么分类
- 它来自什么业务类型
- 它现在是否仍然可用

所以这次新增的不是第二套上传链路，而是一层新的业务资源模型。

## 为什么不能直接继续用 `sys_file`

`sys_file` 很适合保存底层事实：

- 原始文件名
- 保存文件名
- 路径
- URL
- 文件大小
- 哈希

但它不适合直接承载附件中心的管理语义。

如果继续把业务字段都堆进 `sys_file`，很快就会把“底层上传记录”和“业务附件资源”混成一张表，后面别的模块一复用就会越来越难收口。

所以这次实现固定成两层：

```text
sys_file
  ↓
sys_attachment
```

也就是说：

- `sys_file` 负责“文件确实上传成功了”
- `sys_attachment` 负责“这份文件作为后台附件资源该怎么被管理”

## 这次新增了什么表

附件中心新增的是：

- `sys_attachment`

核心字段并不多：

- `file_id`
- `display_name`
- `category`
- `biz_type`
- `uploader_id`
- `status`
- `remark`

这里最关键的是 `file_id`：

> 一条附件中心记录，永远建立在一条已经存在的文件上传记录之上。

所以附件中心不是绕开 `sys_file`，而是显式复用它。

## 后端模块怎么落

当前后端模块目录是：

```text
server/internal/module/system/attachment/
├─ dto.go
├─ entity.go
├─ repository.go
├─ service.go
├─ handler.go
├─ routes.go
└─ policy.go
```

这次它继续留在 `module/system`，原因很直接：

- 附件中心面对的是“全局可管理资源”
- 它天然需要菜单、按钮、状态切换和后台管理页
- 它不是会话内自助能力，也不是单一业务模块私有页面

所以它更接近“系统级通用资源模块”，而不是账户中心那种 `auth` 自助页。

## 为什么这次明确复用文件上传服务

这一轮最重要的结构约束，是：

> 附件中心不能再发明第二套上传实现。

所以当前实现直接复用了 `system/file` 的上传服务，把文件先写进 `sys_file`，再继续创建 `sys_attachment`。

也就是说，附件中心新增的是：

- 业务元数据
- 附件管理接口
- 附件管理页面

而不是：

- 第二套落盘逻辑
- 第二套上传白名单
- 第二套文件命名规则

## 这次补了哪些接口

当前附件中心先补的是最稳的一组管理接口：

- `GET /api/v1/system/attachments`
- `POST /api/v1/system/attachments`
- `POST /api/v1/system/attachments/:id/update`
- `POST /api/v1/system/attachments/:id/status`

它们对应的语义分别是：

- 列表查询
- 上传并创建附件
- 编辑附件元数据
- 启用 / 禁用附件

这里刻意没有先补删除接口，原因和前面几个模块保持一致：

- 先把最常见的创建、维护、状态流转做稳
- 真正的删除策略、历史附件清理和业务引用保护，留到需求出现时再扩

## 前端页面怎么落

当前前端页面是：

- `admin/src/pages/system/AttachmentView.vue`

它不是文件上传页的简单复制，而是围绕附件管理语义做的一页：

- 按名称、分类、业务类型、后缀、状态筛选
- 上传时补附件名称、分类、业务类型、备注
- 上传后可继续编辑附件元数据
- 可以禁用或重新启用附件
- 可以复制附件公开链接

这说明一个很重要的前端判断：

> 底层文件模块负责“把文件放进去”，附件中心负责“让文件成为可管理的后台资源”。

## 权限和菜单为什么必须一起补

附件中心不是一个只在后端存在的公共 API。

这次和代码一起补齐了：

- `system:attachment`
- `system:attachment:list`
- `system:attachment:upload`
- `system:attachment:update`
- `system:attachment:status`

以及对应的：

- `sys_menu`
- `casbin_rule`
- `sys_role_menu`

这样模块一落地，超级管理员就能直接打开、上传、编辑和切状态，而不是再手工补一轮菜单和授权。

## 它和文件管理页的边界怎么区分

这两页现在的职责应该明确分开：

- 文件管理页更偏底层上传记录与 URL 视角
- 附件中心更偏“业务可读、可维护、可筛选”的资源视角

如果后续真的要只查底层文件元数据，继续去文件管理；
如果要站在业务资源角度维护附件，进入附件中心。

## 这一页真正想传达的规范

附件中心最重要的不是“又多了一个模块”，而是这一条接入规则：

> 当仓库已经存在稳定的底层公共能力时，后续企业常用模块应该优先复用它，再在上面补业务语义，而不是复制出第二套基础设施。

## 当前验收结果

附件中心这一轮已经具备最小闭环：

- 后端 `system/attachment` 模块已接通
- `sys_attachment` 表与菜单 / Casbin 种子已补齐
- 前端附件中心管理页已接通动态菜单
- 上传、列表、编辑、状态切换已形成闭环
- 自动化测试已覆盖一条上传并维护附件的成功路径
