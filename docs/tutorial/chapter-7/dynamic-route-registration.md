# 动态菜单注册与按钮权限

后台壳子已经有了，但它真正“活起来”的关键不在布局文件本身，而在菜单和页面路由是动态生成的。

这一页对照当前真实实现，讲清这条链路：

> `/auth/menus` 返回的菜单树，如何变成侧边栏、动态路由，以及页面内可以直接消费的按钮权限码。

::: tip 🎯 本节目标
读完后，你应该能解释三个问题：

1. 为什么当前后台不用手写完整静态业务路由表
2. 为什么按钮权限码可以直接在页面里 `canUse(...)`
3. 为什么退出登录时必须同时清理动态路由
:::

## 先看当前真实文件

这条链路当前主要落在：

```text
admin/src/api/menu.ts
admin/src/router/index.ts
admin/src/router/dynamic-menu.ts
admin/src/layouts/AdminLayout.vue
```

完整关系是：

```text
GET /api/v1/auth/menus
  ↓
getCurrentUserMenus()
  ↓
setAuthMenus(...)
  ↓
buildDynamicRoutes(...)
  ↓
router.addRoute('admin', ...)
  ↓
sideMenuOptions / buttonPermissionCodes
```

## 路由守卫在这里扮演什么角色

当前动态菜单链路不是在登录页里完成的，而是在 `router.beforeEach(...)` 里完成的。

这有两个直接好处：

- 刷新页面后，仍然可以重新拉菜单并恢复动态路由
- 不是只有“刚登录成功那一次”才会注册页面

也就是说，当前系统把“菜单加载”当成了一段登录后运行时初始化，而不是登录按钮点击后的附带动作。

## 当前初始化顺序是什么

当用户访问一个非 `/login` 页面时，路由守卫会按下面顺序处理：

1. 先判断本地有没有 Token
2. 如果没有，就清理旧动态路由并跳回登录页
3. 如果有，但动态路由还没准备好，就请求 `/auth/menus`
4. 把菜单树写进 `authMenus`
5. 把页面菜单转换成子路由并挂到 `admin` 路由下
6. 返回 `to.fullPath`，让当前目标地址重新匹配一次

这一步里最值得注意的是第 6 步。

::: details 为什么动态路由注册后要 `return to.fullPath`
因为用户第一次访问目标地址时，这条页面路由其实还不存在。

只有等 `router.addRoute(...)` 把子路由补进去后，Vue Router 才能重新匹配到真正页面。所以当前实现注册完动态路由后，会立刻让当前地址重新走一次匹配流程。
:::

## `dynamic-menu.ts` 现在实际上做了三件事

这个文件不是单纯的“菜单转换器”，它当前同时承担三类能力：

1. 保存当前登录用户的菜单树
2. 生成 Naive UI 侧边栏菜单
3. 生成动态路由和按钮权限码集合

对应状态分别是：

- `authMenus`
- `sideMenuOptions`
- `buttonPermissionCodes`

这让页面层、布局层、路由层都能围绕同一份菜单源数据工作。

## 为什么要区分目录、菜单、按钮三种类型

当前 `AuthMenu` 有一个非常关键的字段：

- `type`

它决定当前节点到底参与哪一层逻辑：

| 类型 | 前端作用 |
| --- | --- |
| `Directory` | 只参与侧边栏层级组织 |
| `Menu` | 参与侧边栏，也会注册成可访问页面 |
| `Button` | 不出现在侧边栏，用来收集按钮权限码 |

这也是为什么当前菜单树可以同时服务：

- 页面入口
- 路由注册
- 按钮显隐

而不需要再单独请求一份“按钮权限列表”。

## `routeComponentMap` 为什么必须是白名单

当前后端菜单会返回一个 `component` 字段，例如：

- `system/UserView`
- `system/RoleView`
- `system/NoticeView`

但前端不会把这个值直接拼成任意动态导入路径，而是要求它命中：

- `routeComponentMap`

原因是这里有两个风险需要提前拦住：

1. 菜单配置写错时，不应该把前端导入路径搞乱
2. 数据库存的字符串，不应该直接控制任意页面加载

所以当前实现宁可回退到 `PlaceholderPage.vue`，也不会盲目导入未知组件。

## 侧边栏菜单是怎么来的

`sideMenuOptions` 当前是一个计算属性，它会在内置“工作台”菜单之外，再拼接后端返回的页面树。

转换规则大致是：

- 按钮节点不进入侧边栏
- 目录和页面菜单进入侧边栏
- 空目录会被禁用
- 图标通过前端白名单映射

所以侧边栏最终看到的是“面向导航”的结构，而不是数据库里原始菜单表的机械拷贝。

## 按钮权限码为什么能直接在页面里消费

当前 `buttonPermissionCodes` 会递归收集菜单树中所有：

- `type === Button`

的节点 `code`。

这样每个系统页里只要写：

```ts
function canUse(code: string) {
  return buttonPermissionCodes.value.includes(code)
}
```

就能直接控制：

- 新增按钮
- 编辑按钮
- 状态切换按钮
- 上传按钮
- 分配权限按钮

也就是说，当前页面并不关心“这个用户属于哪个角色”，只关心：

> 这个权限码是否存在于当前登录人的菜单授权结果里。

## 图标白名单为什么也值得单独提

当前 `dynamic-menu.ts` 不只对白名单组件做了保护，对菜单图标也是一样：

- 后端只返回字符串标识
- 前端用 `menuIconMap` 命中真正图标组件
- 未知图标回退到默认图标

这一步虽然看起来只是视觉细节，但它延续了和 `routeComponentMap` 一样的设计原则：

> 后端给的是标识，前端掌握最终渲染控制权。

## 为什么退出登录必须调用 `resetDynamicRoutes()`

当前前端把动态菜单和动态路由都看作“当前登录用户上下文的一部分”。

所以退出登录时，不仅要清：

- Token
- 用户信息

还要清：

- `authMenus`
- 已注册的动态子路由
- `dynamicRoutesReady` 状态

否则用户切换账号后，就可能看到上一个账号残留的菜单入口。

## 最小验收方式

这一页理解或改动完成后，至少可以这样验证：

1. 用有系统菜单权限的账号登录，确认侧边栏能展示真实菜单树
2. 刷新页面，确认动态路由能重新恢复
3. 改一个菜单节点的 `component` 为错误值，确认前端只回退到占位页，不会崩
4. 切换不同角色账号，确认按钮显隐会随菜单授权结果变化
5. 退出登录再换账号，确认旧菜单和旧页面入口不会残留
