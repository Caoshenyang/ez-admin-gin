# 日志查询页实现要点

系统页里还有一类非常值得单独拿出来讲的页面，就是日志查询页：

- `admin/src/pages/system/OperationLogView.vue`
- `admin/src/pages/system/LoginLogView.vue`

它们和前面的用户页、配置页不太一样，因为这两张页都不是为了“维护资源”，而是为了：

> 看清系统已经发生了什么。

::: tip 🎯 本节目标
读完后，你应该能理解为什么日志页不需要强行套进新增 / 编辑模式，也知道只读审计页在前端应该把重点放在哪些地方。
:::

## 两张日志页的共同点是什么

它们都属于：

- 只读查询页
- 无新增
- 无编辑
- 无删除

因此它们共同复用的骨架很清楚：

- 查询区
- 表格
- 分页

这让日志页成为一种非常纯粹的前端页面模式。

## `LoginLogView.vue`：最纯粹的只读列表

登录日志页当前重点展示：

- 用户名
- IP
- 状态
- User-Agent
- 时间

它的页面目的很明确：

- 看谁登录过
- 哪次成功，哪次失败
- 从哪里发起

因此它几乎不需要额外交互，只要：

- 能筛选
- 能翻页
- 能快速看状态

就已经完成了主要任务。

## 为什么登录日志页很适合当“最小查询页模板”

因为它几乎没有额外复杂度：

- 不需要写操作弹窗
- 不需要多资源联动
- 不需要树结构
- 不需要详情配置

如果你后面要做一张“纯查数据、不改数据”的页，这张页是非常好的模板起点。

## `OperationLogView.vue`：为什么比登录日志更复杂

操作日志页除了基础查询，还多了几层很实用的可视化处理：

- 风险等级
- 成功 / 失败结果
- 模块识别
- 详情抽屉

这让它不再只是“列出日志”，而是在帮使用者快速判断：

> 哪些操作更值得关注，哪些失败更需要排查。

## 风险级别为什么值得在前端表达

当前 `OperationLogView.vue` 会根据：

- 请求方法
- 是否成功

给日志行打上：

- 高
- 中
- 低

这样的轻风险标记。

这一步不是安全审计的终局，而是一个非常实用的后台体验优化，因为它让使用者在大量日志里能先看出重点。

## 为什么操作日志页要用详情抽屉

日志有一个典型问题：

- 表格里信息放不下

如果把：

- 完整路径
- 查询参数
- 错误信息
- User-Agent

全部塞进表格列，页面会很快失控。

所以当前实现选择把详细上下文放进：

- `NDrawer`

这也是日志页区别于普通只读列表页的关键点：

> 列表负责概览，抽屉负责上下文。

## 操作日志页为什么会解析“模块”

当前页面会从接口路径里再提炼出一个“模块”概念，例如：

- 用户管理
- 角色权限
- 文件管理

这一步虽然是前端展示层逻辑，但它很有价值，因为它把原始 API 路径转换成了更接近后台使用者心智的表达。

## 两张日志页最适合复用到什么场景

### 优先参考 `LoginLogView.vue`

当你的页面：

- 完全只读
- 查询条件简单
- 主要任务是按字段快速过滤

例如：

- 消息发送记录
- 同步任务历史
- 简单事件列表

### 优先参考 `OperationLogView.vue`

当你的页面：

- 需要在列表中表达风险或严重程度
- 单行摘要放不下完整细节
- 更适合用抽屉看详情

例如：

- 审批操作记录
- 任务执行审计
- 安全事件列表

## 当前这类页面为什么也值得单独写

因为后台系统里真正高频的页面，不只是那些能新增编辑的资源页。很多时候，审计和排查页决定的是：

- 系统是否可运营
- 问题是否可追踪
- 风险是否容易暴露

所以第 7 章把日志页单独拎出来，是很有必要的。

## 最小验收方式

理解或调整这两张页后，至少可以这样验证：

1. 进入登录日志页，确认能按用户名、IP 和状态筛选
2. 确认失败登录会和成功登录有清晰区分
3. 进入操作日志页，确认能按方法、路径、用户名筛选
4. 打开一条日志详情，确认抽屉能展示更完整上下文
5. 对比不同请求方法和结果，确认风险展示和颜色区分合理
