# 前端运行时结构

在开始看登录页、动态菜单和系统页面之前，先要把一个更底层的问题讲清楚：

> 当前这个前端管理台，到底是怎么被组织起来的。

如果这一层不稳，后面就很容易出现一种典型混乱：

- 登录逻辑写在页面里一份
- 路由守卫里再写一份
- Token 读取又在请求封装里再写一份
- 动态菜单逻辑散在布局和路由里各一半

这一页先把当前真实前端结构定稳。

::: tip 🎯 本节目标
读完后，你应该能顺着当前代码说清下面这条链路：

- `main.ts` 如何启动应用
- `router/index.ts` 如何接管页面流转
- `api/http.ts` 如何统一带鉴权头
- `utils/auth.ts` 如何保存和清理登录态
- `layouts/AdminLayout.vue` 如何承接后台壳子
- `pages/*` 如何变成最终的业务页面入口
:::

## 先看当前真实目录

现在前端主线主要落在下面这些目录：

```text
admin/src/
├─ api/
├─ components/
├─ layouts/
├─ pages/
│  ├─ auth/
│  ├─ dashboard/
│  └─ system/
├─ router/
├─ styles/
├─ types/
└─ utils/
```

这几层在当前项目里的职责可以先记成下面这张表：

| 目录 | 当前主要职责 |
| --- | --- |
| `api/` | 封装所有后端接口调用 |
| `components/` | 复用型 UI 组件 |
| `layouts/` | 后台页面壳子 |
| `pages/` | 真正的页面级组件 |
| `router/` | 路由入口、动态菜单与动态路由 |
| `types/` | 接口和页面复用的 TypeScript 类型 |
| `utils/` | 登录态、通用工具函数 |

## 应用是怎么启动的

当前启动入口很轻：

```ts
const app = createApp(App)

app.use(createPinia())
app.use(router)

app.mount('#app')
```

这说明当前前端主线里：

- 全局状态能力已经预留给 Pinia
- 页面流转完全交给 Vue Router
- 运行时主线是“应用启动后立即进入路由系统”

也就是说，后面所有登录校验、菜单初始化和页面切换，本质上都会围绕 `router` 展开。

## 当前前端运行主线可以怎么理解

现在这套管理台可以先理解成下面这条链路：

```text
main.ts
  ↓
router/index.ts
  ↓
是否有 Token
  ├─ 没有：进入 LoginPage
  └─ 有：进入 AdminLayout
          ↓
      拉取 /auth/menus
          ↓
      生成动态路由 + 侧边栏
          ↓
      渲染 pages/dashboard/* 或 pages/system/*
```

这条链路一旦看清楚，后面的登录态、菜单和按钮权限就不会再像几段零散技巧。

## `api/` 为什么要单独做一层

当前每个后端资源都已经有自己对应的 API 文件，例如：

- `api/auth.ts`
- `api/menu.ts`
- `api/user.ts`
- `api/role.ts`
- `api/config.ts`
- `api/file.ts`
- `api/notice.ts`

而这些 API 文件最终又统一依赖：

- `api/http.ts`

这一步的价值是把两类职责拆开：

| 文件层级 | 关心什么 |
| --- | --- |
| `api/http.ts` | 通用请求基座、鉴权头、401 处理 |
| `api/*.ts` | 某个资源对应的具体接口 |

这样后面如果你新增一个模块，不需要重新处理 Axios 实例和 Token 请求头，只要沿着当前接口组织方式补一个新 `api/*.ts` 文件就行。

## `types/` 为什么要跟着 API 和页面一起长

当前前端没有把所有类型都塞进页面组件内部，而是把接口数据结构放进：

- `types/auth.ts`
- `types/menu.ts`
- `types/user.ts`
- `types/role.ts`
- `types/notice.ts`

这样做有两个直接好处：

- API 层和页面层可以共享同一份类型
- 当后端响应结构演进时，变更点会更集中

尤其在当前这种“系统模块已经比较多”的管理台里，`types/` 是避免页面脚本越来越臃肿的关键层之一。

## 页面目录为什么分成 `auth / dashboard / system`

当前 `pages/` 目录已经明确按页面性质分组：

| 目录 | 当前用途 |
| --- | --- |
| `pages/auth/` | 登录页 |
| `pages/dashboard/` | 工作台首页 |
| `pages/system/` | 用户、角色、菜单、配置、文件、日志、公告等系统页 |

这和后端第 6 章的模块边界是呼应的：

- 后端有 `module/auth`
- 后端有 `module/system`
- 前端也按“登录 / 工作台 / 系统页”去组织页面入口

现阶段前端还没有大量真实业务页，所以 `system/` 是最主要的页面分组。后面如果开始补业务模块，最自然的延续就是继续新增新的页面分组，而不是把所有东西都继续塞进 `system/`。

## `layouts/` 为什么单独存在

当前后台壳子并不是分散在每个页面里重复写的，而是统一由：

- `layouts/AdminLayout.vue`

承接。

它负责的不是业务页面本身，而是后台共同的那层骨架：

- 左侧菜单
- 顶部栏
- 面包屑
- 工作标签
- 内容区容器

这个拆分很重要，因为它让“页面本身”可以专注于自己的业务内容，而不用每页都重新关心后台壳子怎么长。

## `router/` 在当前项目里不只是静态路由表

这里是当前前端最值得重点理解的一层。

`router/` 现在至少承担了三件事：

1. 基础静态路由注册
2. 登录态路由守卫
3. 动态菜单转动态路由

所以它并不只是一个“路径到页面组件的映射文件”，而是整个管理台运行时组织能力的中心。

后面两节会分别展开这两条更具体的主线：

- 登录态与会话流转
- 后台壳子、动态菜单与按钮权限

## 当前最关键的判断标准

这一页真正要建立的判断是：

> 前端管理台不是一组孤立页面，而是一条由 `main -> router -> auth session -> dynamic menu -> layout -> pages` 串起来的运行时主线。

只要这条主线稳定，后面继续补登录细节、系统页面和业务模块页面时，就不会变成各写各的。
