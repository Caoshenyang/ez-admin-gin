# 用户管理页实现要点

第 7 章前面已经把后台壳子、动态菜单和系统页面模式讲清楚了。现在开始看第一张最有代表性的真实管理页：

- `admin/src/pages/system/UserView.vue`

它很适合当第一个详细案例，因为这张页同时覆盖了当前后台最常见的几种动作：

- 列表查询
- 新增
- 编辑
- 状态切换
- 角色分配

::: tip 🎯 本节目标
读完后，你应该能理解当前用户管理页为什么是第 7 章里最值得复用的“标准管理页模板”，也知道它比普通 CRUD 页多出来的那一层是什么。
:::

## 先看当前真实依赖

用户页当前主要围绕下面这些文件工作：

```text
admin/src/pages/system/UserView.vue
admin/src/api/user.ts
admin/src/api/role.ts
admin/src/api/post.ts
admin/src/types/user.ts
admin/src/types/role.ts
admin/src/types/post.ts
admin/src/router/dynamic-menu.ts
```

从链路上看，它大致是：

```text
query / formModel
  ↓
getUsers / createUser / updateUser / updateUserStatus / updateUserRoles
  ↓
roles / posts / users
  ↓
NDataTable + NModal + NSelect
  ↓
canUse('system:user:*')
```

## 为什么这张页比普通资源页更典型

因为它不只是维护“用户”这一张资源表，还顺带接住了两个很关键的组织关系：

- 用户和角色
- 用户和岗位

这意味着用户页天生就比 `ConfigView`、`NoticeView` 这类轻资源页更复杂，但又没有复杂到像角色页那样进入权限编排模式，所以它刚好处在一个很适合教学的位置。

## 当前页面的第一层骨架是什么

当前 `UserView.vue` 依然沿用第 7 章已经总结过的标准骨架：

1. `query` 管筛选和分页
2. `loadUsers()` 拉列表
3. `formVisible / formMode / formModel` 管新增和编辑弹窗
4. `roleVisible / selectedRoleIDs` 管附加动作弹窗
5. `columns` 管表格展示和操作区
6. `canUse(...)` 管按钮显隐

这再次说明：

> 就算资源变复杂，当前后台也尽量不改变基础页面骨架。

## 查询区现在解决了什么问题

用户页当前的查询区不只支持：

- 关键词
- 状态

还支持：

- 角色筛选

这一步很关键，因为它让“用户页不是只看用户本身”，而是把用户在权限体系里的归属也纳入了管理入口。

## 表格为什么同时展示角色和岗位

当前列表列里最有辨识度的两列就是：

- `role_ids`
- `post_ids`

页面会先通过：

- `roleNameMap`
- `postNameMap`

把 ID 数组转换成标签展示。

这说明前端在这里承担的不是“自己推导业务关系”，而是把已经加载好的辅助资源：

- 角色列表
- 岗位列表

用于更友好的可视化呈现。

## 为什么这里既有编辑弹窗，又有“分配角色”弹窗

这是用户页比普通资源页多出来的地方。

当前页面把用户相关动作分成了两类：

| 动作 | 页面承载方式 |
| --- | --- |
| 用户基础信息维护 | 主表单弹窗 |
| 角色重新分配 | 独立角色弹窗 |

这样拆开的好处是：

- 基础资料和权限归属不会混进同一张表单
- 角色调整可以单独做权限控制
- 页面交互更贴近后台实际使用习惯

## 当前表单模型为什么要带 `post_ids`

这和前面 handoff 的升级方向直接对齐。

当前用户模块已经不只是：

- 用户名
- 昵称
- 状态
- 角色

还正式纳入了：

- 岗位归属

所以 `UserView.vue` 的表单模型里现在会包含：

- `role_ids`
- `post_ids`

也就是说，这张页已经开始承接第 5 章“组织体系与数据权限”落到前端后的实际表现。

## 为什么这张页还保留了 `checkedRowKeys`

当前页面已经有行选择状态：

- `checkedRowKeys`
- `selectedCount`

这一步当前并没有发展成复杂批量操作中心，但它已经表达出一个很清楚的信号：

> 用户页被当成高频管理页对待，未来有扩批量动作的空间。

这也是为什么它比配置页、公告页更像“后台系统核心页”。

## 当前按钮权限是怎么落进去的

用户页现在围绕下面这些权限码决定操作显隐：

- `system:user:create`
- `system:user:update`
- `system:user:status`
- `system:user:assign-role`

这意味着用户页不会问“当前是不是管理员”，而只问：

> 当前账号有没有这个动作对应的按钮权限码。

这正是第 7 章前面动态菜单页里那条按钮权限链路在页面层的真实落地。

## 这张页最适合复用到什么场景

如果你后面要新增一个业务页，同时具备下面特征，就非常适合先参考 `UserView.vue`：

- 有筛选条件
- 有分页
- 有主资源表格
- 有新增 / 编辑弹窗
- 有附加动作弹窗
- 有多种关联资源展示

例如：

- 员工管理
- 客户管理
- 项目成员管理

## 最小验收方式

理解或调整这张页后，至少可以这样验证：

1. 登录后进入“用户管理”，确认列表正常显示
2. 用角色和状态筛选，确认数据会变化
3. 新增一个用户，确认成功提示和列表刷新都正常
4. 编辑用户后，确认昵称或状态真实更新
5. 打开“分配角色”动作，确认角色选择和保存闭环成立
