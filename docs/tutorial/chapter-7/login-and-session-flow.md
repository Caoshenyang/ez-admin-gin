# 登录态与会话流转

后台管理台的第一条关键主线，不是菜单，也不是页面，而是登录态。

因为只要登录态这条线没收稳，后面所有事情都会变得不稳定：

- 登录后跳哪
- 刷新后还能不能留在后台
- 请求什么时候自动带 Token
- Token 失效后怎么回到登录页

这一页就专门讲这条链路。

::: tip 🎯 本节目标
读完后，你应该能顺着当前代码解释下面这条流程：

- 登录页提交用户名密码
- `/auth/login` 返回 Token 和用户摘要
- `utils/auth.ts` 决定把登录态存到哪里
- `api/http.ts` 自动拼接 `Authorization`
- `router/index.ts` 决定未登录、已登录和动态路由初始化时的跳转行为
:::

## 先看当前完整链路

当前登录态主线可以先压成这张图：

```text
LoginPage.vue
  ↓
api/auth.ts -> POST /auth/login
  ↓
utils/auth.ts -> setAuthSession(...)
  ↓
router.push('/dashboard')
  ↓
router.beforeEach
  ↓
有 Token：进入后台并准备动态路由
无 Token：跳回 /login
```

## 登录页现在真实做了什么

当前登录页在：

- `admin/src/pages/auth/LoginPage.vue`

它做的事其实很克制，主要就三步：

1. 表单校验用户名和密码
2. 调 `login(...)`
3. 登录成功后调用 `setAuthSession(...)` 并跳转工作台

这说明当前登录页并没有把大量会话逻辑写死在页面里，而是只承担“登录交互入口”的角色。

## `/auth/login` 返回什么

前端当前期待的响应结构在：

- `types/auth.ts`

核心字段包括：

- `user_id`
- `username`
- `nickname`
- `access_token`
- `token_type`
- `expires_at`

这意味着当前后端登录接口返回的不只是 Token，还会顺手返回前端做会话展示最常用的一组用户摘要。

## `setAuthSession(...)` 为什么是整个登录态的中心

登录成功后，页面不会自己直接操作 `localStorage` 或 `sessionStorage`，而是统一交给：

- `utils/auth.ts`

里面的：

- `setAuthSession(...)`
- `clearAuthSession()`
- `getAccessToken()`
- `getAuthorizationHeader()`
- `getAuthUserInfo()`

这一步的意义很大，因为它把“登录态到底怎么存、怎么读、怎么清”这件事集中到了一个地方。

## 当前为什么同时支持 `localStorage` 和 `sessionStorage`

现在 `setAuthSession(...)` 会根据“记住登录”选项决定存储位置：

- 记住登录：写入 `localStorage`
- 不记住登录：写入 `sessionStorage`

并且读取时会统一从两边兜底查。

这意味着当前会话策略已经具备一个比较实用的后台特性：

> 用户可以自己选择“关闭浏览器后还保留登录态”还是“只在当前会话生效”。

## 为什么请求层要统一拼鉴权头

当前并不是每个 API 函数自己去拼 `Authorization`，而是统一放在：

- `api/http.ts`

里通过 Axios 请求拦截器处理。

逻辑很直接：

1. 如果是公开接口，例如 `/auth/login`、`/setup/init`，就直接放过
2. 否则读取本地登录态
3. 如果有 Token，就拼上 `Authorization: Bearer xxx`

这样做的价值很稳定：

- API 文件更干净
- 登录态来源只有一处
- 后续切换 Token 策略时，不需要逐个改 API 方法

## 401 为什么先在请求层清理本地会话

当前 `api/http.ts` 的响应拦截器里还有一个很关键的动作：

```ts
if (error.response?.status === 401) {
  clearAuthSession()
}
```

这意味着：

- 一旦后端明确说“你已经未授权”
- 前端先把旧的本地 Token 和用户信息清掉

这样能避免一种很常见的问题：

> 本地还残留着过期 Token，前端却一直以为自己还在登录状态。

## 路由守卫如何决定去登录页还是工作台

当前真正决定页面流转的是：

- `router/index.ts`

它的守卫逻辑可以概括成三段：

### 1. 访问 `/login`

- 如果已经有 Token，直接去 `/dashboard`
- 没有 Token，允许进入登录页

### 2. 访问受保护页面但没有 Token

- 清掉动态路由
- 跳回 `/login`
- 同时带上 `redirect` 参数

这意味着后面如果你从未登录状态直接访问某个后台页，系统并不会傻跳，而是会记住你本来想去哪里。

### 3. 已有 Token，但动态路由还没初始化

这时守卫会去请求：

- `/api/v1/auth/menus`

并根据返回结果注册动态路由。

这说明在当前项目里，“有 Token”只是进入后台的第一步，真正能看到哪些页面，还要继续依赖菜单权限树初始化。

## 为什么登录成功后不直接在页面里拉菜单

当前设计里，登录页成功后只做：

- 保存会话
- 跳到 `/dashboard`

而不是自己立刻拉 `/auth/menus`。

原因是当前项目故意把“登录交互”和“后台初始化”拆开：

- 登录页负责用户输入和登录动作
- 路由守卫负责后台运行时初始化

这样后续不管是刷新页面、手动输入某个后台路径，还是首次登录，走的都会是同一条初始化路径，而不会出现“只有从登录页点进来才正常，刷新就坏了”的问题。

## 当前用户摘要为什么也放进会话里

当前 `utils/auth.ts` 在保存登录态时，不只保存 Token，也会把：

- `userId`
- `username`
- `nickname`
- `expiresAt`

一起存起来。

这样 `AdminLayout.vue` 就可以直接拿当前用户显示顶部名称，而不必每次都额外请求一次“我是谁”。

这不是说 `/auth/me` 不重要，而是：

> 在前端运行时层面，本地保留一份最小用户摘要，能让后台壳子启动得更顺。

## 当前这条链路的边界也要讲清楚

### 1. 验证码目前还是占位

登录页界面里已经有验证码交互，但当前还只是前端占位，并没有接入真实后端校验。

### 2. 401 时当前主要是“清会话”

现在响应拦截器在 401 时会清理本地登录态，但具体跳转回登录页，仍然主要交给路由守卫在下一次导航时完成。

### 3. 当前还没有做更复杂的刷新 Token 机制

现阶段这条主线先保证：

- 登录成功能进入后台
- 过期 Token 不会一直脏留在本地

先把最小稳定链路跑通，再谈更复杂的刷新机制，会更符合当前教程阶段。

## 怎么验证这一页讲的链路已经成立

### 1. 登录成功后能稳定进入工作台

在登录页输入管理员账号后，应该能：

- 成功拿到 Token
- 保存本地会话
- 跳到 `/dashboard`

### 2. 刷新后台页后不应直接丢登录

如果使用了记住登录，刷新 `/dashboard` 或其他后台页时，前端应该还能从本地会话中恢复 Token，并继续进入后台。

### 3. 未登录访问后台页会被带回登录页

直接访问例如：

- `/system/users`

如果没有本地 Token，应该会被重定向到 `/login`。

### 4. Token 失效后不会一直假装登录

如果后端返回 401，前端应该会清理本地登录态，避免旧 Token 长时间残留。

## 本节最关键的结论

这一页真正要建立的判断是：

> 当前前端登录态不是一段页面脚本，而是一条由登录页、会话工具、Axios 基座和路由守卫一起组成的统一运行时链路。

只要这条链路稳定，后面的动态菜单、后台壳子和系统页面就有了可靠前提。
