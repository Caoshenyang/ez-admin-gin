# 后台壳子、动态菜单与按钮权限

登录成功只是进入后台的起点。真正让一个管理台“像管理台”的，是进入后台之后的这层运行时组织能力：

- 左侧菜单
- 顶部栏
- 工作标签
- 动态路由
- 按钮权限显隐

这一页专门讲这条链路。

::: tip 🎯 本节目标
读完后，你应该能顺着当前代码说清下面这条流程：

- 路由守卫拉取 `/auth/menus`
- `dynamic-menu.ts` 把菜单树转换成侧边栏、动态路由和按钮权限码
- `AdminLayout.vue` 承接后台壳子和工作标签
- `pages/system/*` 页面通过权限码控制具体操作按钮
:::

## 先看后台初始化后的真实链路

当前后台运行时主线可以先压成下面这张图：

```text
router.beforeEach
  ↓
getCurrentUserMenus()
  ↓
setAuthMenus(menus)
  ↓
buildDynamicRoutes(menus)
  ↓
router.addRoute('admin', ...)
  ↓
AdminLayout.vue
  ├─ sideMenuOptions
  ├─ buttonPermissionCodes
  └─ RouterView
```

这一层把“后端返回的权限树”和“前端真正看到的界面”连接了起来。

## 为什么当前菜单能力围绕 `/auth/menus`

当前前端不会直接拿后台菜单管理接口做运行时菜单源，而是明确使用：

- `GET /api/v1/auth/menus`

原因很清楚：

- `/system/menus` 是后台菜单配置管理入口
- `/auth/menus` 是当前登录用户实际可见的权限树

这和第 3 章已经讲过的职责边界完全一致。

所以当前前端运行时真正依赖的是：

> 当前用户能看到什么，而不是系统里一共配置了什么。

## `dynamic-menu.ts` 现在一共做了几件事

当前 `router/dynamic-menu.ts` 不是一个简单“图标映射表”，它至少承担了四个职责：

### 1. 保存当前登录用户菜单树

通过：

- `authMenus`
- `setAuthMenus(...)`
- `clearAuthMenus()`

维护当前用户的可见权限树。

### 2. 生成侧边栏菜单

通过：

- `sideMenuOptions`
- `buildMenuOptions(...)`

把后端返回的目录和页面节点转换成 Naive UI `NMenu` 可直接消费的数据结构。

### 3. 生成动态路由

通过：

- `buildDynamicRoutes(...)`

把页面菜单节点转换成 Vue Router 子路由，再动态挂进 `admin` 布局路由下面。

### 4. 收集按钮权限码

通过：

- `buttonPermissionCodes`
- `collectButtonCodes(...)`

递归收集所有按钮节点的 `code`，给页面做按钮显隐判断。

也就是说，当前菜单树在前端不是只服务“左侧菜单”，而是同时服务：

- 导航
- 路由
- 按钮权限

## 当前菜单树在前端怎么区分三类节点

当前前端和后端一样，固定使用三类菜单类型：

| 类型 | 说明 |
| --- | --- |
| `Directory` | 目录节点 |
| `Menu` | 页面菜单节点 |
| `Button` | 按钮权限节点 |

在前端运行时里，这三类节点会分别扮演不同角色：

- 目录：主要进入侧边栏树
- 页面菜单：进入侧边栏，同时生成动态路由
- 按钮：不出现在侧边栏，但会进入按钮权限码集合

这就是为什么按钮权限能够跟菜单树走同一份数据源，而不需要单独再拉一条按钮权限接口。

## `component` 字段为什么是关键桥梁

后端菜单树里的页面节点会带一个：

- `component`

例如：

- `system/UserView`
- `system/RoleView`
- `system/NoticeView`

当前前端会在 `routeComponentMap` 里把它映射成真实页面组件。

也就是说，菜单树的页面节点最终并不是直接渲染页面，而是先通过这层稳定映射，变成真正的懒加载路由组件。

这一步的价值很大：

- 数据库里只保存稳定组件标识
- 前端可以自由调整文件位置和 import 写法
- 不认识的组件还能回退到占位页，而不是直接崩掉

## `AdminLayout.vue` 为什么是整个后台壳子的中枢

当前后台壳子统一由：

- `layouts/AdminLayout.vue`

承接。

它至少承担了下面这些职责：

- 左侧折叠菜单
- 顶部栏
- 当前用户显示
- 面包屑文本
- 工作标签管理
- 内容区容器

这意味着：

> 当前后台不是“每个页面自己拼一个菜单栏”，而是所有后台页都先进入统一壳子，再由 `RouterView` 渲染具体业务页。

## 当前工作标签是怎么跑起来的

`AdminLayout.vue` 里已经有一套轻量工作标签逻辑：

- `openTabs`
- `ensureCurrentTab()`
- `handleCloseTab(...)`
- `handleCloseOtherTabs()`

当前它会围绕：

- 当前路由路径
- 当前路由标题

来维护已打开页面标签。

这说明当前前端主线已经不只是“有侧边栏”，而是已经具备一个更接近企业后台使用习惯的页面切换容器。

## 当前用户显示为什么直接来自本地会话

在壳子顶部，当前用户名显示来自：

- `getAuthUserInfo()`

也就是第 7 章上一页讲过的本地最小用户摘要。

这样做的好处是后台壳子启动时不需要额外再请求一次“当前用户是谁”，顶部体验会更顺，首屏也更稳定。

## 按钮权限在页面里怎么真正落地

当前页面层并不会直接拿整棵菜单树自己遍历，而是统一使用：

- `buttonPermissionCodes`

例如公告页和用户页里，都会有类似判断：

```ts
function canUse(code: string) {
  return buttonPermissionCodes.value.includes(code)
}
```

再通过：

```vue
<NButton v-if="canUse('system:notice:create')">
```

控制按钮显隐。

这一步非常关键，因为它说明：

- 按钮权限不是某个页面自己手写常量开关
- 而是来自后端统一授权结果

## 为什么按钮权限和接口权限不能混为一谈

虽然两者都和权限有关，但职责不同：

| 能力 | 当前作用 |
| --- | --- |
| 接口权限 | 后端决定请求能不能进 |
| 按钮权限 | 前端决定某个操作入口显不显示 |

一个最常见误区是：

> 接口有权限了，前端按钮就一定显示。

其实不是。当前项目里这两条线虽然都来自角色授权，但它们分别由不同机制承接：

- 接口权限走 Casbin
- 按钮权限走菜单树按钮节点

两条线最好同时成立，后台体验才完整。

## 当前菜单图标为什么也值得单独理解

前端并不会直接拿数据库里任意图标字符串去渲染，而是通过：

- `normalizeMenuIcon(...)`
- `menuIconMap`

先做白名单映射。

这样做的好处是：

- 数据层和组件实现解耦
- 错误图标值不会把页面打挂
- 整体风格更可控

这也是当前动态菜单实现比“数据库里直接写组件名”更稳的一点。

## 这条链路对系统页面意味着什么

当前 `pages/system/*` 下的这些页面之所以能统一工作，靠的并不只是它们各自会调 API，而是它们都共享了：

- 同一后台壳子
- 同一菜单初始化机制
- 同一动态路由入口
- 同一按钮权限来源

这就让“系统页是一套散装页面”的风险大幅降低。

## 当前实现里几个值得先讲清楚的边界

### 1. 当前动态菜单主要围绕系统页展开

现阶段主要映射的还是：

- `pages/system/*`
- `pages/dashboard/*`

后续补真实业务模块时，只需要继续往这条链路上加新的页面映射和菜单种子即可。

### 2. 搜索菜单入口目前还是 UI 占位

`AdminLayout.vue` 顶部已经有搜索输入框，但当前主要还是结构预留，不是完整菜单检索能力。

### 3. 当前工作标签是轻量实现

已经能满足页面切换和关闭其他，但还没有做到更复杂的标签持久化和缓存策略。

现阶段先把基础后台壳子跑稳更重要。

## 怎么验证这一页讲的链路已经成立

### 1. 登录后能看到按权限生成的侧边栏

如果 `/auth/menus` 返回菜单树，后台左侧菜单应该能跟着变化，而不是完全依赖前端静态配置。

### 2. 访问受权页面时会注册动态路由

当前路由守卫首次初始化后台时，会基于菜单树动态添加页面路由。

### 3. 页面按钮显隐应随按钮权限码变化

例如公告页、用户页里，创建、编辑、状态切换等按钮都应受到按钮权限控制。

### 4. 退出登录后旧菜单和动态路由会被清理

当前退出登录不仅会清本地登录态，也会执行：

- `resetDynamicRoutes()`
- `clearAuthMenus()`

这样能避免“切换账号后还残留上一个账号菜单”的问题。

## 本节最关键的结论

这一页真正要建立的判断是：

> 当前前端后台壳子，并不是一个静态布局模板，而是一套围绕后端权限树实时组织菜单、路由和按钮权限的运行时系统。

只要这条线稳定，后面继续补系统页面和真实业务模块页面时，前端就能沿着同一套主线继续扩。
